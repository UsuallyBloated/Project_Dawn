# Session 2026-07-30 — server-authoritative weapon procs (PD_W0025)

Built the first item off the swing-rate gate's follow-up list: procs are now server-authoritative.
The user chose the flavored path (keep the "Flaming Strike for N (Critical!)" feel, server-driven)
and to build it now.

## What shipped
A cross-boundary feature (protocol + gdext GDExtension + server + client + data), built via an
understand survey then implemented + adversarially reviewed. Server `b0bdbdd` / client `ad145c0`.

- **Server roll (`tick.rs`).** On each accepted, landed melee swing (enemy branch), the server rolls
  the SERVER-derived weapon's `proc_chance`; on a proc it folds `proc_damage` into THAT swing's
  resolution — subtract from `entity.hp`, add to `aggro`+`threat` for the attacker — so the existing
  single HealthUpdate + death/loot/xp block handles a proc killing blow ONCE (credited to the
  attacker, no duplicate cascade, no zombie mob). Gated on `entity.hp > 0` (no proc-on-corpse). Flat
  5% proc crit (x1.5-2.0) mirrors the old client feel; no elemental resist (server has no
  enemy-resist model). This was the low-risk seam: no `apply_spell_damage_to_enemy` refactor, no
  synthetic Spell.
- **New wire message `ProcTriggered`** (appended to `ServerWorldMsg`; `WORLD_PROTOCOL_ID` -> PD_W0025),
  sent PRIVATELY to the attacker so the client renders the named proc hit; the mob HP drop is already
  fanned to everyone via the combined HealthUpdate. gdext bridge surfaces a `proc_triggered` signal
  (all four sites: decl / Incoming / emit / mapping).
- **Client render.** `remote_player_manager._on_proc_triggered` resolves the target node, spawns the
  number, plays the elemental flash, logs "<proc_name> for N (Critical!)" — same flavor, now driven
  by the server's roll. Removed the client-side `_try_fire_proc` (both call sites + the function) so
  the client no longer rolls/sends procs.
- **Data bug fixed.** `proc_damage_type` is authored in the client's `SpellData` enum space
  (FIRE=0), which is offset from the wire enum. Flamebrand was tagged `1` = ICE, so the fire sword
  procced ICE. Corrected to `0` (FIRE) in `items.toml` + the `.tres`, and added
  `proc_damage_type_to_wire` (mirror of the client `_spell_to_net_damage_type`). +2 tests.

## Security posture
The proc reads `server_weapon_path` (the server equipment map, from the finding-5 gate), not the
client's claim, so a modified client can't fabricate a proc weapon; the proc fires only on an
accepted swing (already bounded by the swing-rate limit). The old client-sent proc Attack (which
double-hit) is removed, and even a resent one is a same-hand Attack the swing-rate limit drops.

## Adversarial review (3 lenses)
Correctness + regression lenses CLEAN; exactly one LOW (integration): the `WORLD_PROTOCOL_ID` bump is
a wire marker, not a connection gate — the client takes its protocol_id from the server-minted token,
so a stale client still connects and just ignores `ProcTriggered` (decode -> Raw, no crash). To
refuse out-of-date clients on a real host, raise the auth `min_client_version` at deploy. Clarified
this in the protocol doc-comment; no functional change needed. The review's deep verification
confirmed no double-count, correct proc-kill crediting, reliable-ordered send-before-EntityDied, and
full client/server element agreement.
