# Session 2026-10-01 — The security and ops batch, and what the review caught

The user is still away from the desk. With the scale-readiness pair built the day before, the
next work that needed neither the user nor a desk was the small security and ops batch from the
To-Do: the `InspectPlayer` range gate, the GM action audit log, and the ban tool. All server-side
on the deploy branch, no protocol change. Nothing touched the R720. Playtest:
`inspect_range_gm_audit_ban_checklist.md`.

## What was built

- **`InspectPlayer` range gate** (server `3523bd1`, client `cd9f1d1`; exploit audit finding 10a).
  A paperdoll used to be readable from anywhere in the world. The inspect drain now requires the
  two players within `INSPECT_RANGE` (30 m), written keep-only-when-in-range so a non-finite
  distance refuses (the NaN Move lesson). The client checks its own tighter 20 m first, so an
  honest player gets a clean line and never meets the server gate.
- **GM action audit log** (server `b47aadb`). The `gm_actions` table has existed since the first
  migration and the audit was deferred "to a fast follow" when per-account `is_gm` shipped in
  July. Six dev-gated handlers now record what an authorized account issued; `admin_report`
  shows the newest 50 rows on the console and as a card in the HTML report.
- **`admin_account` bin** (server `81150c7`): list, `ban <username> [reason]`, `unban <username>`.
  `is_banned` was enforced at login and nothing could set it.

## What the review changed (`30f0474`)

The session-workflow review returned fifteen findings. Several changed the design, which is the
case for running it before pushing rather than after.

- **The audit cap dropped the row but still ran the command.** The first cut capped a connection
  at 8 audit rows per tick and counted the overflow. Past the cap each command still executed,
  so a GM client could bury a coin grant behind eight harmless fillers, and the Test Panel's own
  crafting-materials button (about 34 gives in one frame) lost most of its rows. The gate and
  the audit are now one call, `PerConnection::authorize_dev_cmd`: a command runs only if its row
  was queued, and a command that cannot be recorded is refused. The bound is a per-connection
  token bucket (burst 128, refill 8 a second), so writes are bounded over time and not just per
  tick. `via` now names every authority in force (`gm`, `dev`, `gm+dev`); before, a GM on a
  server started with `PD_DEV_CMDS` read as a clean `via=gm` row, masking exactly the footgun
  the tag exists to reveal. `reap_connection` flushes its own connection's queue.
- **The ban had a race.** A login in flight when the ban landed read `is_banned = false`, spent
  its Argon2 verify, and inserted its session after the ban's purge had committed: a banned
  account holding a session good for 30 minutes. `touch_session` now refuses a banned account on
  every redemption, and the world server refuses it at connect (`KickCode::BannedNow`, a code
  that already existed in the protocol and had never been sent), which covers a connect token
  minted just before the ban. What a ban still does not do is remove a character already in the
  world; that is its own new To-Do item (kick by account).
- **The inspect refusal leaked.** "You are too far away to inspect <name>" for far targets and
  silence for absent ones made the gate a char_id to name map and an is-online oracle for anyone
  enumerating ids. Far, offline and never-existed now get one generic line and the same empty
  result.
- **The ops bins could create a database.** `admin_account`, `grant_gm` and `reset_password`
  defaulted to `mode=rwc`. On the R720 the source tree and the live data are different
  directories, so a tool run from the source tree quietly left an empty `world.db` there that
  looks real to the next tool. They default to `mode=rw`, and `admin_account` parses its
  arguments before opening anything.

## Found along the way

- **Charm had no range check at all.** Reading the charm arm to fix a test showed it validated
  only that the target id was a live enemy, so a modified client could charm any mob in the
  world by id from anywhere. It now has the nuke arm's reach (25 m). The integration test runs
  the exploit as a client would: the caster names the id of a mob two cells away that it was
  never told exists. Worth a sweep of the other target-type arms for the same gap; recorded on
  the new To-Do entry.
- **The last flaky test had a cause.** `charm_converts_enemy_to_pet` varied under load for weeks
  and always passed alone. It waited for a skeleton's hit, then cast a 2.0 s Charm while that
  skeleton kept swinging every 2.5 s, so the cast finished about 0.2 s before the next swing and
  any stretch of the test loop rolled the ~70% interrupt. It now charms a dev-spawned mob that
  never swings. The review rightly pointed out that this dropped coverage of the case that
  matters in play, so a second test charms a Bonepile skeleton that is mid-fight with a SECOND
  client: a spawner-owned mob with a live target, threat table and swing timer, and nothing
  swinging at the caster.
- **A lesson for harness tests.** My first out-of-range charm test walked the caster 41 m from a
  dummy. In a loaded run the same loop took longer in wall-clock time, the server (which
  integrates movement in real time) carried the character further, it strayed into a camp, and
  the cast was interrupted by a mob. Never let distance depend on wall-clock time: seed
  positions through the `characters` table instead. Recorded in
  `server/docs/flaky_integration_tests.md`.

## Deliberately not built

Account delete and the purge of soft-deleted characters. The 2026-09-17 wipe retired the

characters except `gm_actions`, which now has rows: a delete must first decide what happens to
audit history. Recorded on the To-Do entry and in the `admin_account` bin's header.
