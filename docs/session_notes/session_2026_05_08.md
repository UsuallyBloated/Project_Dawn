## Clean window-close disconnect — five rounds to find the right shape

The handoff plan called for `_notification(NOTIFICATION_WM_CLOSE_REQUEST)` calling `leave_session()` so the server logs `client requested disconnect` instead of a 10 s heartbeat-timeout kick. The straightforward implementation hit three different bugs in sequence; this section records each so the next person doesn't re-derive them.

### Round 1: `_notification` doesn't fire on autoload nodes in Godot 4

Initial implementation:
```gdscript
func _notification(what: int) -> void:
    if what == NOTIFICATION_WM_CLOSE_REQUEST:
        leave_session()
```

Test result: 10 s heartbeat-timeout kick. The handler never ran. In Godot 3 the close-request notification propagated down the scene tree; in Godot 4 it is delivered only to the root `Window` node and does not propagate to children (autoloads sit under the root viewport, so they're children).

### Round 2: `auto_accept_quit = false` set inside the handler is too late

Tried setting `get_tree().auto_accept_quit = false` inside `_notification` and calling `get_tree().quit()` at the end. Same result — the engine commits to quitting based on the value at the time the close request fires, not at the time the handler reads it.

### Round 3 (works): `Window.close_requested` signal

In Godot 4, the canonical pattern is:

```gdscript
func _ready() -> void:
    get_tree().auto_accept_quit = false
    get_tree().root.close_requested.connect(_on_close_requested)
    ...
```

Set `auto_accept_quit` *before* any close request can fire, connect to the root window's `close_requested` signal (which the engine emits regardless of the auto-quit setting), and call `get_tree().quit()` ourselves at the end of the handler. `_notification` was removed entirely — it's the wrong path for this in Godot 4.

After this fix, the handler ran and the server log changed: heartbeat timeout disappeared, replaced by a fast `client disconnected (transport) reason=Transport`. Progress, but still not the goal — `client requested disconnect` was still missing.

### Round 4 (didn't help): server-side drain-before-evict

Hypothesis: when the client calls `disconnect_now()` after `send_disconnect()` + a few polls, the netcode-level disconnect packet races the app-layer `Disconnect` message at the server. Both arrive in the same UDP burst; renet's `transport.update()` queues both a `ClientDisconnected` event AND the channel-0 message; tick.rs processes events before draining channels, so the `ClientDisconnected` event handler removes the connection from `connections` HashMap, then the channel-drain phase skips the disconnected client (`if !connections.contains_key(&client_id) { continue; }`), losing our app message.

Server-side fix attempt at [crates/projectdawn-server/src/world/tick.rs:86-113](F:/Projects/server/crates/projectdawn-server/src/world/tick.rs#L86-L113): drain pending channel messages *inside* the `ClientDisconnected` event handler before removing from `connections`.

Test result: `client requested disconnect` still missing. The drain inside the disconnect handler always finds nothing, because `RenetServer` evicts per-client channel buffers as part of `transport.update()` itself — by the time the `ClientDisconnected` event reaches our `match` arm, `server.receive_message(client_id, channel)` already returns `None`. The drain is structurally correct logic but doesn't recover what's already been freed.

The drain is **kept** as defensive code with a "why" comment — if a future renet version preserves channel buffers across disconnect, or if there's any scenario where messages persist past the event, it'll catch them. Cheap to leave in place; expensive to re-derive if removed.

### Round 5 (works): client skips `disconnect_now()`, OS closes the socket on exit

The actual fix is on the client side: stop sending the netcode-level disconnect at all. `Net.leave_session()` now sends the app-layer `Disconnect` and drives `poll(0.05)` 4× (~200 ms) to flush the message to the wire — and that's it. No `disconnect_now()`. The OS closes the UDP socket when the process exits a few milliseconds later.

Server side then sees only the app-layer message (no concurrent netcode disconnect packet), processes it cleanly:

```
15:21:41  client requested disconnect          char_id=8                         ← handlers::handle_message
15:21:41  client disconnected (transport)      client_id=8 reason=DisconnectedByServer
```

`reason=DisconnectedByServer` because tick.rs handles `Outcome::Disconnect` from the message handler by adding the client to `to_disconnect` and calling `server.disconnect(client_id)` itself — that's the right cause.

The downside: `leave_session()` no longer cleanly tears down the renet client object. For the current callers (window-close, in-game Quit) the process exits immediately after, so the GC handles it. A future return-to-lobby flow that needs to keep the process alive would need a different teardown path — `send_disconnect`, poll long enough for the message to be processed (~50–100 ms is plenty given a 50 ms server tick), *then* `disconnect_now()`. Documented in the function's comment.

## Quit Game button (`scripts/options_screen.gd`)

The in-game Quit Game button at [options_screen.gd:109-112](scripts/options_screen.gd#L109-L112) was calling `SaveManager.save() ; get_tree().quit()` directly, which bypasses `Window.close_requested` entirely (that signal only fires for OS-initiated closes). Routed it through the same cleanup:

```gdscript
func _on_quit_pressed() -> void:
    SaveManager.save()
    Net.leave_session()
    get_tree().quit()
```

Both quit paths (OS X button, in-game Quit Game) now share `Net.leave_session()` as the single source of truth for network teardown. `leave_session()` early-outs gracefully when `_state != CONNECTED_APP`, so it's safe to call in local-save mode.
