## 1. The skills-accessibility arc (three commits, one morning)

The tester could not run the active-skill checklist at all: "None of the skills are accessible by
the player." The old route — right-click an empty hotbar slot, "Assign Skill..." — showed an empty
list from their seat while a headless probe showed `Skills.available` correctly holding
Slash/Pummel/Shield Bash for a Warrior. Three responses, in order:

- **`6d2e9a4` diagnostics.** `Skills.setup_for_class` now logs class + count to the debug
  console, and `PlayerStats.apply_character` errors loudly on an unknown race/class key instead
  of crashing character init invisibly (verified headlessly: a lowercase race key aborts the
  function mid-way with no trace — the engine error never reaches `debug.log`).
- **`274f015` the Skills tab.** The book window (B) became a TabContainer: Spells tab (existing
  flow untouched) + a Skills tab listing `Skills.available` with stamina/cooldown columns and
  tooltips. Tab visibility follows list emptiness — pure melee auto-select Skills, casters see
  only Spells, hybrids get both.
- **`c697cde` pickup-and-place.** The user dropped the Assign Skill menu outright ("I don't want
  the 'Assign Skills...' approach"): left-click a skill in the tab, its name rides the cursor as
  a gold ghost label (owned by `SocialHotkeys.begin_skill_carry`), left-click an empty hotbar
  slot to place. ESC or re-clicking cancels; occupied slots are inert while carrying so placing
  can never fire an ability. The menu item, popup and both handlers are deleted.

The playtest then passed §1-3 of the guards checklist — so the tab populated correctly live,
which means the old menu's empty list died undiagnosed. The `6d2e9a4` console lines stay in
place; if any class ever shows an empty Skills tab, they name the cause.

hit-while-casting row never fired — zero `interrupted (hit during cast)` lines in the log — so
it carries. Tick waits on one 15-second re-check: cancel and touch nothing.
