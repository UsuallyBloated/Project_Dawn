## Sub-task 1 — SaveManager close hook + single quit owner

**Problem (audit #1, #2).** `SaveManager._notification(NOTIFICATION_WM_CLOSE_REQUEST)`
doesn't fire on autoloads in Godot 4 — same pitfall Track 1 hit
([session_2026_05_08.md Round 1](session_2026_05_08.md#round-1-_notification-doesnt-fire-on-autoload-nodes-in-godot-4)).
Closing the game with the OS X-button silently skipped the local
save; bounded by level-up / zone-change / explicit-Quit autosaves
but anything done since the last of those was lost. Latent
follow-on: once #1 was fixed, both `Net._ready()` and
`SaveManager._ready()` would call `auto_accept_quit = false` and
both connect to `close_requested`, racing on `get_tree().quit()`
with order determined by autoload-declaration order.

**Fix.** SaveManager becomes the single quit owner. Its
`close_requested` handler calls in order:

1. `SaveManager.save()` — local autoloads, untouched by network teardown.
2. `Net.leave_session()` — flushes app-layer Disconnect, ~200 ms poll.
3. `get_tree().quit()`.

Same sequence the in-game Quit Game button has used since Track 1
([options_screen.gd._on_quit_pressed](../../scripts/options_screen.gd)).
After this change all three quit paths (OS X button, Quit Game,
future return-to-lobby) converge on the same flow. `Net._ready()`
no longer touches `auto_accept_quit` and no longer connects to
`close_requested`; the `_on_close_requested` handler in `net.gd` is
gone entirely.

**Files touched.**
- [autoloads/save_manager.gd](../../autoloads/save_manager.gd) — `_notification` → `_on_close_requested`, save → leave_session → quit. Top-of-file docstring updated.
- [autoloads/net.gd](../../autoloads/net.gd) — `auto_accept_quit` ownership and `_on_close_requested` removed from `_ready()`.

Commit `ba61229`.

## Sub-task 2 — Lobby UI gating in launcher mode (audit #3)

**Problem.** Lobby UI was ungated when `Net.is_launcher_mode()`
returned true. The Solo / Host / Join / Test Room / Test Dungeon
buttons all assumed offline / legacy-ENet state, but `Net` was
already pumping heartbeats (and after Track 1, movement intents)
to the live world server. Clicking Test Dungeon in particular
caused the dungeon fall-through Track 2 surfaced — first-tick snap
teleports X/Z to whatever world.tscn position the server has
saved, dropping the player off the dungeon's floor mesh.

**Fix.** Per user choice (handoff defaulted to auto-route on
connect; user picked the explicit-button variant), lobby in
launcher mode shows a "Connecting to world..." status until
`Net.app_connected` fires, then surfaces an explicit "Enter
World" button. Click it → `world.tscn` loads. If
`Net.app_disconnected` fires, the local-mode buttons re-appear so
offline dev iteration works when the server is unreachable.

**Watch-out covered.** `Net._ready()` runs before lobby `_ready()`
(autoloads first), but the renet handshake is async — typical state
at lobby load is `CONNECTING_TRANSPORT`, not `CONNECTED_APP`. The
lobby code handles the rare race where the handshake completes
before the lobby loads via `if Net.is_app_ready()` and a direct
call to the connected handler.

**Files touched.**
- [scenes/lobby.tscn](../../scenes/lobby.tscn) — added `EnterWorldButton` (hidden by default).
- [scripts/lobby.gd](../../scripts/lobby.gd) — `_setup_launcher_mode`, `_on_app_connected`, `_on_app_disconnected`, `_on_enter_world_pressed`. Local-save mode (`else` branch) unchanged.

Commit `13ffb5d`.

## Sub-task 3 — Server-side per-tick movement integration

**Problem.** [handlers.rs Move arm](../../../server/crates/projectdawn-server/src/world/handlers.rs)
applied `pos += dir × MAX_MOVE_SPEED × TICK_DT` inline every time a
Move message was accepted. Client physics-tick rate (~60 Hz) vs
server tick (20 Hz) → multiple Moves per tick → ~3× speedup. Track
2 papered over this client-side with a 20 Hz Move throttle, but
the bug stayed fragile under variable arrival rates and would
re-surface in Track 3 multi-client testing.

**Fix.** Move arm now stores latest direction intent on
`PerConnection`; the tick loop integrates exactly once per tick,
between the message-drain and broadcast phases. Stale-move
threshold (`STALE_MOVE_THRESHOLD = 500 ms`) zeroes the integrated
direction if no Move has arrived recently — protects against a
crashed client running forward visually until the 10 s heartbeat
timeout fires.

```rust
// world/tick.rs, between message-drain and broadcast:
let dt = TICK_DT.as_secs_f32();
for conn in connections.values_mut().filter(|c| c.ready) {
    let dir = match conn.last_move_received {
        Some(t) if now.duration_since(t) < STALE_MOVE_THRESHOLD => conn.latest_direction,
        _ => Vec3f::ZERO,
    };
    conn.pos.x += dir.x * MAX_MOVE_SPEED * dt;
    conn.pos.y += dir.y * MAX_MOVE_SPEED * dt;
    conn.pos.z += dir.z * MAX_MOVE_SPEED * dt;
}
```

**Behavior unchanged for healthy clients.** One integration per
tick × the same scaled magnitude the client sends. Track 2's
20 Hz throttle stays — it's now redundant rather than load-bearing,
but harmless and useful as a bandwidth cap. Track 2 walk feel
verified identical post-fix.

**Vec3f::ZERO** drops its `#[allow(dead_code)]` — first reader is
the tick loop's stale-input guard.

**Files touched.**
- `crates/projectdawn-server/src/world/mod.rs` — `STALE_MOVE_THRESHOLD` const.
- `crates/projectdawn-server/src/world/connection.rs` — `latest_direction` + `last_move_received` fields on `PerConnection`.
- `crates/projectdawn-server/src/world/handlers.rs` — Move arm stops integrating per-message, drops unused `MAX_MOVE_SPEED` / `TICK_DT` imports.
- `crates/projectdawn-server/src/world/tick.rs` — new step 5 (per-tick integration); imports updated; trailing step numbers renumbered.

**Verification.** `cargo test --release` 6/6 passing
