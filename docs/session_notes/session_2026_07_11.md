# Session 2026-07-11 — Exploit audit (read-only security review)

Both repos surveyed, branch `fix/xp-leveling-overflow`. **No code was changed.** This was a
read-only security review at the user's request ("comb the project and document anything a
player could use as an exploit," explicitly excluding the active quest-XP re-tune work). The
deliverable is a review-first findings document:
[../security/exploit_audit_2026-07-08.md](../security/exploit_audit_2026-07-08.md).

Note on the date label: the audit file is named / titled `2026-07-08`, but the review
actually ran 2026-07-10 into 07-11. Left the filename as-is to avoid breaking the open
reference; the content is what matters.

## Method

Five parallel read-only analysis passes over both repos, each reading the real handler and
apply code rather than inferring from names: economy; item duplication and theft;
combat/progression; session/auth/movement; and a message-by-message enumeration of the whole
client-to-server trust boundary. Every significant finding was then re-read against source in
the main session before being written down (the always-verify rule). All five passes
independently converged on `/give` as the top issue, which raises confidence it is real.

## Findings (nothing fixed, for review first)

- **Critical: ungated `/give` (GmCommand).** Any in-world client mints any registry item,
  free and persisted (also an unlimited coin source via vendor resale). It is a dev command
  simply missing its `is_dev`/`is_gm` gate, unlike its siblings. Reachable from the stock
  client's `/give` chat command. `handlers.rs:1221` / `tick.rs:5623`.
- **High: no server-side melee swing-rate limit** (attack-speed hack). The server applies
  every `Attack` with no per-player cooldown; there is no swing-timer field on
  `PerConnection`. `tick.rs:2562`.
- **High: `Respawn` floors HP to 25% while alive** (no death check, repeatable survival
  floor). `handlers.rs:764`.
- **Medium:** `CastSpell` has no class/level gate except the resurrection arm (`tick.rs:3371`
  is the only one); `Attack` trusts the client `weapon_path` (damage from an unequipped
  weapon); no login rate limiting or lockout; `BuyItem` ignores `vendor_id`.
- **Low:** cross-store transfers persist as separate transactions (crash-window dupe or loss;
  the corpse path is the only atomic one); username enumeration; minor info-disclosure and
  cosmetic gaps (InspectPlayer range, EquipItem slot-type, movement wall-clip, Hit/Miss/Evade
  spoof).
- **Confirmed but kept out of the doc by request (adjacent to the active quest work):**
  `CompleteQuest` does not verify objectives. The server checks only that the quest id exists
  and is not already completed, then pays; objective completion is client-tracked
  (`quests.rs`, `tick.rs:7014`).

Dev tools are flagged with a flag marker in the doc so they can be triaged separately (the
fix for a flagged item is usually "gate the dev tool," not "rework gameplay logic").
Operational caveat recorded in the doc: `is_dev` is the process-wide `PD_DEV_CMDS` env var,
so a shared server booted with that flag exposes all dev commands to every connected client.

## Framing (the pattern behind the findings)

The server validates magnitudes well (damage, XP, heal amounts) but under-validates
eligibility and timing (which weapon you used, which spell your class/level can cast, whether
it is time to swing, whether you are dead, whether you finished the quest). Classic-MMO rule
going forward: client sends intent only, server decides both what it produces and whether it
was allowed.

## Confirmed server-authoritative (assurance)

Identity and impersonation (signed renet ConnectTokens, actor always derived from the
connection), auth crypto (Argon2 + parameterized SQL), movement (no teleport/speed/fly),
damage and heal magnitudes, XP/leveling totals, economy math, loot rights, resurrection
refund, groups and pets, duplicate-login refusal, and combat-log/camp (no escaping death).
Full list in the doc's "correctly defended" section.

## Open / next

Review the doc, then decide fix order. Suggested priority in the doc: (1) `/give` gate,
(2) swing-rate limit + Respawn dead-check, (3) cast class/level gate + weapon_path,
(4) login rate limiting, (5) the low-severity items. Not committed to git.

# Session 2026-07-11 (2) — First race model: Gnome

Wired the first per-race character model. Until now every player (local and remote) rendered
as the authored 2 m capsule; Gnomes now use `gnome.glb`.

## What changed
- Exported `Project_Dawn_Source/models/characters/gnome/gnome.glb` into
  `assets/models/characters/gnome/gnome.glb` (Godot can only import under `res://`) and
  ran a headless import (`.import` + cached `.scn` generated).
- New `scripts/race_model.gd` (`RaceModel`) — a `MODELS` dict of race to
  {scene, feet_y, yaw, hide_nodes} plus a static `apply(mount, race)` that hides the capsule
  mesh and mounts the model under the existing `Visual` node. No-op for races not in the dict,
  so it grows one race at a time without touching the scenes.
- `scripts/player.gd` `_ready` (local branch) and `scripts/remote_player.gd` `_ready` both call
  `RaceModel.apply(...)` — the local player from `PlayerStats.race`, remote peers from the
  `race` the manager sets pre-add (delivered on `EntitySpawn`). So a gnome reads as a gnome to
  everyone, not just to themselves.

## Notes / decisions
- The glb is an early **blockout**: separate cube body-parts, no rig, no animations, no
  materials/textures. It renders as a static, default-material (grey/white) figure that does
  not walk-animate yet. Authored height ~1.09 m, which matches the canonical Gnome height
  (0.90–1.05 m in `docs/reference/creature_heights.md`), so **no scale factor** is applied.
- Mounted the model under `Visual` (the capsule node) so the existing first-person hide
  (`visual.visible = false`) cascades to it; `apply()` subtracts `Visual`'s local Y so feet
  still land on the ground. `feet_y = -0.12` lifts the model so it isn't sunk.
- Hid `Gnome_Framework` + the two `2D_Model_*` reference nodes as modeling scaffolds
  (reversible via `hide_nodes` in the dict).
- **Cosmetic only:** collision, camera height (pivot at 1.6 m) and nameplates still use the
  2 m capsule, so on a ~1.1 m gnome the camera sits above the head. Per-race collision/camera
  tuning is a separate pass (multipliers already sketched in creature_heights.md).

## Needs an in-editor eyeball (can't verify headlessly)
- Facing direction: `yaw` defaults to 0; flip to `PI` in the dict if the gnome faces backward.
- Confirm hiding `Gnome_Framework` was right (should be a scaffold, not body).

Verified: asset imports clean; all three scripts recompile with no parse errors. Not committed.

# Session 2026-07-11 (3) — Race expansion design pass (docs only)

Brainstormed and framed the next wave of races. **No code changed**; nothing is in
`data/character_data.gd`. Working doc: [../design/race_expansion_brainstorm.md](../design/race_expansion_brainstorm.md).

## Decisions
- **Three in-design playable races**, each with a framed race file (draft banner, TBD
  markers) on the `felhari.md` template plus draft stat blocks and racial abilities in
  the new "In Design" section of `race_stats.md`:
  - **Aerathi** ("the Stoop-kin") — cliffside raptor-coded martial race; game-high AGI 99;
    Glide / Raptor Sight / Talons / Stoop / Hollow Bones. `docs/concepts/races/aerathi.md`

    (+50% Languages gain, ties into the planned `hear_language()` wiring) / Songblood /
    Vivid Plumage. `docs/concepts/races/vesperin.md`
  - **Sylphari** — plant-blooded grove keepers; game-high WIS 95; bark-skin + seasonal
    aspect + flowering hair + bioluminescent sap + lichen-marking aesthetic;
    Photosynthesis / Barkskin / Sapblood / Rooted. `docs/concepts/races/sylphari.md`
- The two Avian cultures are **two distinct races** (the game has no sub-race mechanic);
  names user-picked, "Sylari" rejected as too close to Sylphari, "Stoop-kin" kept as the
  Aerathi lore epithet.
- **NPC factions greenlit:** Sporeborn (mushroom folk), Saurian (jungle venom ambushers),
  bog-stalkers (marsh east of Khala), canopy-dwellers (non-Avian).
- **Late idea captured:** faction-driven appearance changes — high Sporeborn standing
  grants mushroom-like cosmetic features; generalized commitment markers per faction
