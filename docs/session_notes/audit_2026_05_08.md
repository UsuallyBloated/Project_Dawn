## 🔴 1. SaveManager autosave-on-window-close is a no-op

[autoloads/save_manager.gd:38-42](../../autoloads/save_manager.gd#L38-L42)

```gdscript
func _notification(what: int) -> void:
    if what == NOTIFICATION_WM_CLOSE_REQUEST or what == NOTIFICATION_WM_GO_BACK_REQUEST:
        if not _is_loading:
            save()
        get_tree().quit()
```

This is the same pattern the Track 1 session ([session_2026_05_08.md
Round 1](session_2026_05_08.md#round-1-_notification-doesnt-fire-on-autoload-nodes-in-godot-4))
proved doesn't work in Godot 4: `NOTIFICATION_WM_CLOSE_REQUEST` is
delivered to the root `Window` only, no propagation to autoloads.
`Net` was migrated to `get_tree().root.close_requested.connect(...)`
in `_ready()`; `SaveManager` was missed.

Effect: closing the game with the OS X-button **does not save** the
character. Autosaves still run on level-up and zone-change; the
in-game Quit Game button explicitly calls `SaveManager.save()` before
quitting (options_screen.gd:110). So the loss window is bounded —
anything done since the last level-up / zone-cross / explicit-Quit
is dropped on a window-close exit.

Suggested fix: same migration as `net.gd:50-57`. Connect to
`get_tree().root.close_requested` in `_ready()` and call `save()`
+ `get_tree().quit()` from the handler. Drop `_notification`.

## 🔴 2. Two autoloads racing for `auto_accept_quit = false`

`Net._ready()` ([autoloads/net.gd:56](../../autoloads/net.gd#L56)) and
`SaveManager._ready()` ([autoloads/save_manager.gd:36](../../autoloads/save_manager.gd#L36))
both set `get_tree().auto_accept_quit = false`. Once #1 above is fixed
and SaveManager moves to `close_requested`, both handlers will run on
window-close and both will call `get_tree().quit()`. The first one to
fire wins; the second is a no-op (tree already shutting down) but
ordering is determined by autoload-declaration order in
`project.godot`, which is brittle.

Suggested fix when fixing #1: pick one owner of window-close.
Cleanest is to have `SaveManager` call `Net.leave_session()` itself,
then save, then `get_tree().quit()` — and remove the ownership from
`Net._ready()`. Mirrors what `options_screen.gd._on_quit_pressed`
already does.

## 🟡 3. `Net` connection lives but lobby UI is ungated in launcher mode

When the game is spawned by the launcher, `Net` autoload connects to
the world server during the lobby scene. The lobby ([scripts/lobby.gd](../../scripts/lobby.gd))
still shows Solo / Host Game / Join Game / Test Room / Test Dungeon
buttons with no awareness that a server-authoritative session is
already live.

A user could click "Solo" or "Test Room" and end up in single-player
local-save mode while `Net` is sending heartbeats and (after Track 1)
movement intents to the live server. No code path actually breaks —
`Net` is independent from `Network` (the legacy ENet autoload) — but
the state machine is incoherent.

Suggested fix: in lobby, if `Net.is_launcher_mode()` returns true,
hide the Solo/Host/Join/Test buttons and auto-load the character + jump
to `world.tscn`. Or render a single "Enter World" button. This is
groundwork Track 3 will need anyway; flag-and-ignore is fine until
then.

## 🟡 4. `dungeon_world.gd` ignores multiplayer state

[scripts/dungeon_world.gd:14-22](../../scripts/dungeon_world.gd#L14-L22)
unconditionally calls `_spawn_player(1, ...)` after dungeon
generation. No `Network.is_online` branch like
[scripts/world.gd:18](../../scripts/world.gd#L18) has.

Currently moot — the only entry to `dungeon_world.tscn` is the lobby's
"Test Dungeon" button which forces `Network.is_online = false`. But
the moment dungeons become reachable from a multiplayer session
(Track 7), client peers will see an empty dungeon while only the host
spawns.

Suggested fix when Track 7 starts: copy the host/client RPC pattern
from `scripts/world.gd:23-43` into `dungeon_world.gd._on_dungeon_ready`.

## 🟡 5. Procedural dungeon: addon vs standalone have drifted

`F:/Projects/Project_Dawn/addons/procedural_dungeon/` and
`F:/Projects/ProceduralDungeon/dungeon_gen/` are both live. The handoff
plan ([handoff_post_track_d.md Track 7](handoff_post_track_d.md#track-7--procedural-dungeon-integration))
says "Not yet integrated into Project_Dawn" but the addon is already
in place, registered in `project.godot`, referenced by
`scenes/dungeon_world.tscn`, and reachable from the lobby.

Diff between the two copies (recursive):
- `dungeon_light_placer.gd`: addon split `DEBUG_LABELS` into
  `DEBUG_TORCH_LABELS = false` + `DEBUG_COMPASS = true`; standalone
  still has the unified `DEBUG_LABELS = true`.
- `dungeon_spawner.gd`: addon gates `print_debug_groups()` calls
  behind `DEBUG_TORCH_LABELS`; standalone always prints.
- All `.uid` files differ (expected — Godot regenerates per project).

Suggested direction: pick a canonical source. Either declare the
addon the upstream and retire the standalone repo, or set up a
sync script. The Track 7 plan's git-submodule option would close
this for good.
