## Opened

Four findings, none of them item loss.

**1. Buying with a full inventory looks like the item vanished.** The server is right and the
client lies. It refuses and charges nothing, but `vendor_window.gd` prints *"Ordered X for Y"* the
instant it sends the request, before the server has answered. **This is the same shape as the
`MoveItem` rejection fixed three days ago**: the server logs a refusal, `continue`s, and tells the
client nothing, so the client can never learn it was wrong. Every `BuyItem` rejection arm does it.
`ChatMessage` already exists and the client renders it, so a fix can be server-only.

**2. Bank coin deposit will not break a larger coin.** `6s` from `1p 5g 5s 75c` is refused rather
than breaking a gold. The four tiers are deliberately independent stacks, so this is a design call.

**3. Coin normalises through a corpse, changing its weight.** `312c` came back as `3s 12c`. Value
identical, but weight is charged flat per coin, so 312 coins became 15 and the player returned
lighter than they died. Minor, and exploit-shaped: die to shed coin weight.

**4. Stack All scope.** A request to consolidate only within a container. The note is cut off, so
the wanted rule needs confirming before anything is built.

## The pattern, still holding

Every Phase 3 item closed so far was recorded under a cause that was wrong, and today added
another: the To-Do said named mobs "lost" their enrage and drops, when in fact **they were never
placed in the world at all**. Nothing anywhere ever set `named_mob_id`.

Finding 1 is the same lesson from the other direction — a rejection that goes unreported is
indistinguishable, from the player's seat, from the game eating something. That is now the third
place the pattern has appeared (MoveItem, and now BuyItem), which suggests it is worth auditing
every `continue`-after-`tracing::info!` in the intent handlers rather than waiting to trip over
them one at a time.
