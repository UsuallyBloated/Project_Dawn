# Session 2026-08-17 — Phase 3 opens: the bank was never eating anything

First Phase 3 item ("Stop it eating their things"). Client-only change, one file:
`scripts/bank_window.gd`. Playtest: `bank_vault_display_checklist.md`.

---

## The bug was in the name

The To-Do called this *"Bank Items-tab does not live-refresh on deposit"*, and that title sent
the diagnosis in the wrong direction. The refresh was never broken. Traced the whole chain and
every link was already correct:

1. Server stores the item and sends a `BankItemSnapshot` after **every** store
   (`world/tick.rs:6519`, via `handlers::send_bank_item_snapshot`).
2. `gdext-net` decodes it (`lib.rs:2619`) and emits `bank_item_snapshot`.
3. `Net._on_bank_item_snapshot` re-emits `world_bank_item_snapshot` (`net.gd:1175`).
4. `BankerManager._on_bank_item_snapshot` rebuilds the cached vault array and emits
   `vault_changed` (`banker_manager.gd:78-91`).
5. `BankWindow._refresh_vault` repaints that grid.

Step 5 ran every single time, on time, and drew **nothing**.

`_make_vault_cell` built a cell containing exactly two things: a `TextureRect` for the icon and
a `Label` for the stack count. So for a freshly deposited item:

- `entry["item"].icon` is **null**, so the texture is blank.
- `count.text` is `""` because the count label is deliberately hidden for a stack of 1.

A null texture over an empty label is pixel-identical to an empty slot. The item was in the
vault, in the cache, and on screen the whole time, rendered as nothing.

**`ItemData.icon` is null for all 172 items in the game.** Verified three ways rather than
assumed: `@export var icon: Texture2D = null` is the declared default, zero `.tres` files under
`data/loot/items/` define an `icon`, and nothing assigns one at runtime (the only writer is
`item_data.gd:142`, restoring from a snapshot's `icon_path`, which is empty when the source had
no icon). So this was not an edge case for unusual items; it was every item, always.

## Why only the bank

`inventory_window.gd:268-271` has had the answer all along:

```gdscript
icon_rect.texture = null if is_drag_source else item.icon
name_label.visible = (not is_drag_source) and item.icon == null
name_label.text = item.item_name
```

A name-label fallback whenever the icon is null. Inventory and bags have it, which is exactly
why an iconless game still renders a readable inventory. The bank vault cell was written without
it and was the only icon grid in the client missing it.

Checked the siblings: `bag_window.gd` already has the fallback; `vendor_window.gd`,
`loot_window.gd` and `inspect_window.gd` render text lists rather than icon grids, so they were
never exposed. The bank vault was the only gap, and it is now closed.

## The fix

Mirrored the inventory's fallback into `_make_vault_cell` / `_refresh_vault`: a centered,
auto-wrapping name label shown when `icon == null`, plus a tooltip naming the item, its count
when greater than one, and the right-click-to-withdraw hint. Empty cells now explicitly clear
the label and tooltip too, so a withdrawn item leaves no ghost text behind.

No server change, no protocol bump, no gdext rebuild. It needs a client re-export to reach a
tester, like every client fix.

## Worth remembering

The misleading part is that this presented as *data loss* ("items disappear when I bank them")
and was in fact a *missing label*. The server logs said `bank store item` the entire time, which
was the clue that the write path was fine. It sat near the top of the friends-build list for
weeks as the highest perceived-severity bug, and the whole of it was one absent `Label`.

The To-Do entry has been renamed to describe the real symptom, so the next person to read it is
not sent after a refresh bug that does not exist.

### The stale-description sweep

A doc sweep found the old "refresh bug" framing in more places than expected, and two of them were
tester-facing, where a wrong known-issue does the most damage:

- `README_FOR_TESTERS.md` told testers outright *"The window just fails to refresh."* Removed; the
  build this ships with has the fix.
- `docs/deployment/inviting_a_player.md` pre-warned every new tester about it. Removed.
- `docs/deployment/server_operations.md`'s triage table gave operators the wrong mechanism. Rewritten
  to be build-aware: ask for `/version`, since a build older than `8ad7f39` genuinely still has it.
- `docs/schedule.md`'s Phase 0 recap also still called it "bank Items-tab refresh".

Deliberately left alone: the dated handoff notes and the original tester repro. Those correctly
record what was believed at the time and are history, not current claims.

had all seven marked. The `.md` was the stale copy this time, the reverse of the drift that
prompted the two-file rule. Added the missing markers (is_gm, Respawn dead-check, melee swing-rate

# Second Phase 3 item: bags opened on the wrong mouse button

`banker_slice2_checklist.md:57`, carried as untriaged since 2026-06-19. Client-only:
`scripts/inventory_window.gd` + `autoloads/inventory.gd`. Playtest:
`bag_click_grammar_checklist.md`.

## Not stale bag items

The standing guess, recorded in the To-Do, was that these were *"stale pre-grammar bags"* created
before the inventory/cursor work. That was wrong, and it is worth naming because it is the second
item today whose written description pointed away from the cause.

It was a code branch. `_on_cell_input` called `_toggle_bag()` from the **left**-click path
(`inventory_window.gd:363`) *and* from the right-click path (`:343`). So both mouse buttons opened
a bag, and a bag could never be picked up or rearranged at all. Nothing about the bag items
differed; a brand-new bag behaved identically.

The grammar has been explicit about this since 2026-06-18
(`inventory_interaction_grammar.md` §3):

| Verb | Target | Intended |
|---|---|---|
| Left-click | any non-stackable, incl. a bag | lift it onto the cursor, no dialog (line 51) |
| Right-click | any, no container open | use / equip / **open a bag** (line 55) |

Left-click now begins a drag like any other non-stackable. Right-click is untouched.

## Bags can move now, which is new

The fix makes bags movable for the first time, so two things that were previously unreachable
became reachable. Both are handled here rather than left to be discovered in a playtest.

**A non-empty bag cannot move.** The server enforces this independently
(`bag_at_base_is_nonempty`, `world/inventory.rs:577`; `move_across` rejects with *"bag must be
emptied before moving"* at `:998`, and the drop path rejects at `:907`). `inventory.gd`'s own
comment at `:108-111` already relied on that invariant to justify dropping a bag's contents Vec on
a clear. So the data was never at risk. But the *experience* would have been: pick up a non-empty
bag, drop it, server silently rejects, bag snaps back with no explanation. In a phase named "stop
it eating their things", a silent snap-back is exactly the wrong feel. New
`Inventory.bag_has_contents()` mirrors the server rule client-side and refuses up front with
"Empty the bag before moving it."

**Bag windows are keyed by base slot index, not by the bag.** A window could therefore outlive the
bag that opened it and sit showing a slot that no longer holds one. `_close_orphaned_bag_windows()`
runs on refresh and frees any window whose slot is no longer a bag. This was latent and unreachable
before, since bags could not move.

Checked the siblings: `bag_window.gd` has no bag-type click branch (correct, there is no
bag-in-bag) and `paperdoll_window.gd` has none either. The inventory window was the only place.

## Pattern worth noting

Two Phase 3 items closed today, and in **both** the written description named the wrong mechanism:
"does not live-refresh" for a bug that was a missing label, and "stale pre-grammar bags" for a bug
that was a duplicated call. Both descriptions had been carried forward unexamined for weeks. The
cheap lesson is that an untriaged item's *stated cause* is a hypothesis, not evidence, and reading
the code first cost minutes in both cases.
