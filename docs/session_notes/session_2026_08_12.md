# Session 2026-08-12 — Respawn at bind, a real death state, and the test suite

Two threads. The headline is the **respawn death-loop** raised by the first external tester on
08-11; the second is a **test-suite triage** that turned out not to be flakiness at all.

Built 08-12, playtested 08-13, regression-swept 08-14. Commits: server `9e42a76`, `c576d75`,
`97c7fac`; client `973e846`, `80cbf55`, `ddf3819`. Playtest: `respawn_bind_checklist.md`.

---

## 1. The respawn death-loop

**What the tester hit.** She died, respawned exactly where she fell, next to the two mobs that
had just killed her, and died again twenty seconds later. Server log, 08-11:

```
02:46:06  server-detected player death char_id=2
02:46:11  damage again
02:46:26  dead again
```

Two corpses, no way out. For a brand-new player with no gear and no warning, that is the worst
experience the game currently offers.

### The root cause was not the missing bind point

This is the part worth remembering. The obvious reading is "there's no bind system, so respawn
falls back to the death site." That is wrong.

`Respawn` restored HP but **never touched position at all**. The client seeded its own respawn
move in `player_death.gd`, but the server owns position, so the very next Position broadcast
dragged the player straight back to the corpse. A client-side fix was structurally impossible.
The bind system was needed anyway, but the loop would have persisted even with a bind point
until the server started sending a teleport.

### What was built

- **Server-authoritative respawn.** `handlers.rs` `Respawn` now computes
  `conn.respawn_destination()` and returns `Outcome::RespawnTeleport { pos }`. Destination is
  your bind point, else `STARTER_SPAWN`, never the death site.
- **Bind points, persisted.** Migration `0011` adds `bind_x/y/z` REAL. The pre-existing
  `bind_zone` column is reused; `bind_entry` / `bind_zone_name` stay dormant (they modelled the
  old client-local save). `PerConnection` gained `bind: Option<BindPoint>`.
- **`BindAtCurrentLocation` woken up.** It was an inert wire variant with no sender *and* no
  handler. Now it has both, gated on alive-and-in-world. gdext gained
  `send_bind_at_current_location` (`c576d75`), which is why this needed a client re-export.
- **Sister Maelis, Soul Binder**, at the town spawn, via a new `bind_soul` dialogue action.
- **A death lock.** `Move` returns early while `conn.death_processed`, so a corpse can't walk.
  Binding is refused while dead for the same reason: no binding where you fell.

### Two follow-ons the playtest found

- **Mobs kept beating the corpse.** The tick's player-snapshot filter was `c.in_world` only, so
  dead players stayed valid aggro targets. Now filtered on `c.hp > 0.0`, and `newly_dead` wipes
  `entity.aggro` / `threat` and clears `entity.target` (`97c7fac`).
- **The corpse twitched on movement keys.** The client still ran its movement prediction while
  dead. `player.gd` now zeroes velocity and returns early at the top of `_physics_process` when
  `PlayerDeath.is_dead` (`80cbf55`).

### Verifying the bind was genuinely used

§3/§4 of the checklist were inconclusive by geometry: Maelis sits at `(-2, 0, 5)`, only about
5.4 units from `STARTER_SPAWN (0,0,0)`, so "respawned at bind" and "respawned at the fallback"
look nearly identical on screen. Settled with a DB read instead: after die, respawn, do not
move, log out, the character's stored `pos` equalled `bind_x/z` to every decimal
(`-3.16501545906067 / 2.23090076446533`), where the fallback would have written 0/0.

### Deliberately not included

Post-respawn invulnerability. A safe respawn location should make it unnecessary; revisit only
if a playtest disagrees.

## 2. The integration suite was not flaky

`world_two_clients.rs` had sat at a stable `29 passed; 13 failed` for three weeks and was being
treated as flakiness. It was neither flakiness nor a server regression.

The file was last edited 07-19 and **three gates landed after it**, so the fixtures were
asserting pre-gate behaviour:

- The **CastSpell class/level gate** broke 11 tests casting spells a level-1 character cannot
  have (three of them also as the wrong class).
- The **melee swing-rate limit** broke a test bursting 10 Attacks in a single frame, correctly
  dropped as forgery.
- The **`meditate` skill** took the casting-key count from 6 to 7.

Fixed the fixtures, not the server (`6a1a92e`), and corrected the flaky-tests doc, most of which
described this stale-fixture problem rather than real timing flakiness (`db3df02`). The suite
went from 29/42 to 40-42/42.

**Practical rule going forward: a failure outside the three known-flaky tests is a real
regression.** Those three are `aoe_spell_damages_nearby_enemies`, `pet_attacks_owners_target`
and `pet_pulls_aggro_via_threat_reaggro`; all pass in isolation and vary run to run. Making them
deterministic (wait on enemy AI state, not wall-clock) is still open.

One further fixture fix rode along in `97c7fac`:
`player_attack_kills_enemy_and_corpse_despawns` paced its swings at 700 ms against a 0.65 s
bare-hand floor, a 50 ms margin that lost under load. Widened to 1000 ms. Proven not to be a
regression from the aggro change by an A/B full-suite run with the change stashed.
