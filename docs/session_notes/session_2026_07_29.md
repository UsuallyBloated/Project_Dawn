## (built section — retained for detail)
The last combat gate. No swing timer existed, so a modified client could spam `Attack` for an
attack-speed hack. Server `335b5b1`.

**Built with two workflows (ultracode):**
1. *Understand* — 3 parallel surveys mapped the swing-timing surface: the server AttackIntent
   resolver (no rate gate; `last_attack_at` is a hand-agnostic regen marker, do not overload), the
   weapon-delay/haste model (`weapon_delay` seconds, fists 2.0, off-hand x1.5, max modeled haste 0.5,
   player haste a server no-op), and the client cadence in `combat.gd` (`maxf(0.5, delay*(1-haste))`,
   Attack sent only on a landed hit, no burst — so only reject "too fast"). Key constraint:
   dual-wield emits two independent Attack streams that co-fire in a tick, so the gate MUST be
   per-hand.
2. *Adversarial review* — 3 lenses (false-positives / bypasses / correctness) against the real code.

**The gate.** New per-hand `conn.last_swing_at[2]` (0 main / 1 off). Per Attack, derive the equipped
weapon (finding-5 map) -> `weapon_delay` -> `min_swing_interval_secs = weapon_delay x handMult x
(1-MAX_HASTE) - grace`, floored 0.4s; if the same hand swung more recently, drop silently (no Miss).
Timestamp advances only on an accepted swing. Assumes max haste so hasted players never trip; mirrors
`combat.gd` constants. +2 unit tests.

**Review findings folded in (6 total: 1 high, 3 med, 2 low):**
- **HIGH bypass — fixed:** an off-hand `Attack` with an EMPTY slot 1 was a forged free ~0.8x-fist
  second damage stream (pre-existing since finding 5). Now rejected (a bare hand is not an off-hand
  weapon; a stock client only sends is_offhand=true when dual-wielding a real slot-1 weapon).
- **MED false-positive — fixed:** grace raised 0.25 -> 0.35 so a fully-hasted player on a remote
  server (Phase 2) keeps margin above realistic internet jitter.
- **MED proc interaction — scoped to a To-Do (not a gate weakening):** a proc weapon's client-sent
  second same-hand Attack is now dropped. Pre-change the server resolved it as a FULL weapon-damage
  roll (procs were double-hitting), NOT the authored `proc_damage`. Correct fix = server-authoritative
  procs (all proc fields already in `items.toml` + the `Item` struct) + client stops sending the proc
  Attack. Filed under Combat/weapons. Base swing is unaffected; client still shows the proc visual.
- **MED "floor loose vs un-hasted" — deliberate residual:** we assume max haste because the gate
  can't tell a hasted client from a non-hasted one (haste is client-paced), so a forged non-hasted
  client can swing up to the fully-hasted rate (~2x). Accepted — the gate kills wire-speed spam;
  exact-cadence enforcement waits on server-authoritative haste. (The suggested "haste=0" fix would
  false-positive every legitimately-hasted player.)
- **LOW drift — documented:** if a future weapon's client `.tres` `weapon_delay` is faster than its
  `items.toml` value the gate could false-reject; none exist today (all >= 2.0, matched). Keep them
  in lockstep.
- **LOW test gap — fixed:** extracted `swing_too_fast()`, added a decision test + fast-weapon deltas.
