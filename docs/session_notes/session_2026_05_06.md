- Wire helpers: `encode_auth(msg) -> String` wraps `JSON.stringify`; `decode_auth(text) -> Variant` returns `null` on parse failure or non-Dictionary payload.
- `CLIENT_VERSION = "0.1.0"` — matches the server's `MIN_CLIENT_VERSION` default. Bump in lockstep.

## Architecture decisions

- **Single-scene UI**: `scenes/main.tscn` is one Control node with `main.gd` attached. The three views (Login / CharSelect / CharCreate) are MarginContainers built programmatically in `_ready()`, all anchored full-rect, toggled via `show()` / `hide()`. No per-view `.tscn` files — keeps everything reviewable in one place and dodges hand-written scene-file parser surprises.
- **Race/class lineup hardcoded** in `scripts/character_lists.gd` (16 races + 18 classes pulled from CLAUDE.md). Pulling `data/character_data.gd` from the client would have dragged in autoload dependencies (PlayerStats etc.) that the launcher does not need. Server validates the chosen race/class on CharCreate, so launcher-side drift surfaces as a server `InvalidInput` error rather than silently breaking.
- **NetProtocol copied** to `scripts/net/protocol.gd`, verbatim from `Project_Dawn/scripts/net/protocol.gd`. Diffed at commit time to confirm zero drift. Both files mirror the Rust protocol crate; keep them in lockstep on every protocol change.
- **Auth host** is editable on the login screen, defaults to `127.0.0.1:8765`, persists to `user://launcher.cfg` along with last-used username. World endpoint is **not** launcher-configured — it comes back in `LoginOk.world_endpoint` and the launcher passes it through to the game.

## `autoloads/auth_client.gd`

- WebSocketPeer wrapper with separate signals: `connected` / `disconnected(was_open)` / `connection_failed(reason)` / `message_received(msg)`.
- Polled every frame in `_process`. Early-returns when never connected, so the autoload sits dormant until the first `connect_to` call.
- State transitions guarded: `connected` only fires on the OPEN edge, `connection_failed` only fires on CLOSED-after-CONNECTING (server unreachable), `disconnected` only fires on CLOSED-after-OPEN (server dropped us mid-session).
- `connect_to(url)` closes any existing peer first so retries don't leak. `send_msg(msg)` no-ops with a `push_warning` if the socket isn't open.

## `scripts/main.gd`

- Login → CharSelect → CharCreate flow:
  - **Login**: validates non-empty fields, queues `make_login` and connects. Server's `LoginOk` stores `session_token` / `account_id` / `is_gm` / `world_endpoint` / `characters`, saves config, switches to char select.
  - **Register**: stashes the password in `_password_pending`, sends `make_register`. On `RegisterOk` auto-sends `make_login` with the held password — user lands on char select in one round trip without re-typing.
  - **CharCreate**: sends the chosen name/race/class. On `CharCreated` re-fetches `CharList` and switches back to the select view (server's `CharCreated` reply is just `{char_id}` so a refresh round-trip is needed to render the new entry).
  - **CharDelete**: same refresh pattern via `CharList`.
  - **Logout**: sends `Logout`, waits for `LogoutOk` to tear down the socket.
  - **Error** reply surfaces as `Error (<code>): <msg>` on the status line; connection stays open so the user can correct credentials and retry.
- `_send_or_queue(msg)`: sends immediately if the socket is open, otherwise queues into `_pending_msg` and triggers `connect_to`. The `connected` signal handler drains the queue. This is what lets the user click Log In once and not worry about whether they're already connected.
- Status line shared across all three views via `_set_status(text)` writing to all three Labels' `.text` (only one view is visible, so the user always sees current status).
- Mid-session disconnect (server kicks us, network blip): `_on_ws_disconnected` clears the token and bounces back to login with "Connection lost. Please log in again."

## Game .exe handoff

`_resolve_game_exe()` looks in three places, first hit wins:

1. `$PROJECTDAWN_EXE` if set and points to an existing file
2. Sibling of the launcher executable: `<launcher_dir>/ProjectDawn.exe` (packaged distribution case)
3. Dev fallback: `F:/Projects/Project_Dawn/builds/ProjectDawn.exe`

If none resolve, the launcher reports the failure on the status line without quitting. On success it spawns `OS.create_process(exe, args)` and the launcher's `get_tree().quit()`s. Args passed:

```
--auth-token=<64-char hex>
--char-id=<i64>
--world-endpoint=<host:port>
--client-version=<semver>
```

The game executable does **not** parse these yet (no world UDP server, no CLI arg handler). They're harmless extras the game ignores; the user lands in the existing client lobby. The handoff *mechanism* is exercised end-to-end though — when the game-side parser ships, the launcher side is already done.

# Track C — Pre-flight research & handoff plan (continuation, same day)

User asked for explicit research before writing any Rust. Did three rounds:

## renet version research

- **Current stable: renet 2.0** (released January 2026). The design doc's `0.0.16` sketch is outdated.
- Architecture: core `renet` crate (channels + reliability) + transport (`renet_netcode` for UDP). Two-layer auth model.
- `ServerAuthentication::Unsecure` exists but means any process reachable on the port can establish a connection. The application-layer `session_token` rejects unknown sessions at the first packet, but the connection-establishment surface is wider than necessary.
- `ServerAuthentication::Secure` uses `ConnectToken`: 32-byte private key shared between auth and world subsystems. Auth signs a token after validating the user's session; client uses the token to establish the renet connection; server validates with the same key. UDP packets are encrypted.

## MMO persistence pattern research

Sources: prdeving.wordpress.com MMO architecture article, plantbasedgames.io blog, GameDev.net threads, HN discussion on WoW realm architecture. Consensus pattern matches `server_design.md` §9 already:

- Source of truth = in-memory; DB is a persistence medium for crash recovery, not live state.
- Save selectively, not constantly. WoW-style: position every ~30s (proposing 60s for our case), inventory every change as one atomic SQL transaction (entire dupe-prevention strategy), zone change full save, level-up full save, logout full save.
- No client-driven save calls once the world server is online — `SaveManager.save()` autoload becomes a no-op (per design doc §19).

## Security audit (all three repos)

- ✓ No secrets currently committed. Verified via grep for `api[_-]?key`, `secret[_-]?key`, `private[_-]?key`, `aws_access`, hardcoded password patterns. Single match in `Project_Dawn/.claude/settings.local.json` is a literal `test-key-smoke` placeholder, not a real key.
- ✓ `.env` never committed in any repo (`git log --all --full-history -- .env` returned empty for all three).
- ✓ `.env.example` files contain only placeholders.
- ✓ Argon2id with default OWASP-current params for password hashing (~50 ms per attempt).
- ✓ 256-bit session tokens via `OsRng::fill_bytes`.
- ✓ All SQL queries parameterized with `bind()`; no injection surface.
- ✓ `error.rs` sanitizes `Internal` errors to "internal server error" — never leaks server-side detail to the wire.
- ✓ No password / token / netcode-key logging at any tracing level.
- ✗ No login rate limiting. Bounded by argon2 cost (~10/sec). Not catastrophic for friends-only Tailscale alpha; add before public hosting.
- ✗ No TLS on the WebSocket. Relies on Tailscale WireGuard inside the tailnet. Acceptable for alpha; **must add before going public**.

## Decisions baked into the handoff plan

1. **renet `Secure` mode from day one**, not `Unsecure`. User's instruction was "absolutely no shortcuts when security is in question." Costs ~1 day; gives cryptographic guarantee that only auth-issued connections succeed, encrypted UDP packets, and no rip-and-replace later.
2. **`WorldConnectToken` handed off via temp file, not CLI arg.** CLI args show in `ps` / Task Manager output. Launcher writes to a tempfile with restrictive permissions, passes `--world-token-path=<path>`. Game reads, immediately deletes, then connects.
3. **Position checkpoint cadence: 60 s** (design doc says 5 min — shortened, SQLite WAL writes are cheap).
4. **Server refuses to start without `PROJECTDAWN_NETCODE_KEY` env var.** No silent default-key fallback.

## renet 2.0 API verification

`renet = "=2.0.0"` and `renet_netcode = "=2.0.0"` (released 2026-01-20) confirmed on crates.io via the JSON API. Pinned with `=` so an incidental 2.0.x bump can't change wire behavior. API surface walked from docs.rs before writing any code:

- `RenetServer::new(ConnectionConfig)` / `RenetClient::new(ConnectionConfig)` — both take the same connection-config struct (server_channels_config + client_channels_config).
- `ChannelConfig { channel_id: u8, max_memory_usage_bytes: usize, send_type: SendType }` — `SendType::ReliableOrdered { resend_time }` / `ReliableUnordered { resend_time }` / `Unreliable`.
- `NetcodeServerTransport::new(ServerConfig, UdpSocket) -> Result<Self, Error>`. `ServerConfig { current_time: Duration, max_clients, protocol_id, public_addresses, authentication: ServerAuthentication::Secure { private_key: [u8; 32] } }`.
- `ConnectToken::generate(current_time, protocol_id, expire_seconds, client_id, timeout_seconds, server_addresses, user_data, private_key)` → `write(&mut impl Write)` to serialize / `read(&mut impl Read)` to deserialize.
- `ClientId = u64` (type alias, not a newtype).
- `transport.send_packets(&mut server)` returns `()` on the **server** side but `Result<(), NetcodeTransportError>` on the **client** side — caught by the first compile pass.

## DB helpers

- `db::verify_char_owned(pool, account_id, char_id)` — gates `RequestWorldToken` so a logged-in player can only mint tokens for their own characters.
- `db::load_character(pool, char_id)` — returns `CharacterSpawn` (id, account_id, name, level, hp/mp/stamina, zone, pos, yaw). Called from the world tick loop on `ServerEvent::ClientConnected`.
- `db::checkpoint_position(pool, char_id, zone, pos, yaw)` — single-row UPDATE of `pos_x/y/z`, `yaw`, `zone`, `last_played_at`. No schema migration needed; columns from `0001_init.sql` already cover this.

## Auth handler change

New `RequestWorldToken` arm in `auth::dispatch`: validates session via `touch_session`, verifies char ownership via `verify_char_owned`, then calls `world::mint_connect_token(cfg, advertised_endpoint, char_id, account_id)`. `account_id` is packed into the ConnectToken's 256-byte `user_data` (first 8 bytes, little-endian) so the world server can attribute the connection back to an account on the renet `ClientConnected` event without an extra DB round-trip. Token validity: 30 seconds; netcode timeout: 15 seconds.

## World module structure

```
crates/projectdawn-server/src/world/
├── mod.rs          # public surface: serve, serve_with_socket, bind_world_socket, mint_connect_token
├── connection.rs   # PerConnection state (Vec3f, last_packet, dirty-tracking)
├── handlers.rs     # decode/dispatch ClientWorldMsg → Outcome::{Continue,Disconnect}
├── tick.rs         # 20 Hz scheduler; owns the connection HashMap (no locking)
└── persistence.rs  # 60s checkpoint loop
```

`tick::run` is the heart of it. Each 50ms tick:

1. `transport.update(TICK_DT, &mut server)` — drain UDP, run netcode handshakes.
2. Drain `ServerEvent` queue: `ClientConnected` ⇒ load character from DB, build `PerConnection`; `ClientDisconnected` ⇒ final dirty-row checkpoint, drop entry.
3. Per-client per-channel `receive_message` drain → `bincode::serde::decode` → `handlers::handle_message`.
4. App-layer heartbeat timeout (10s) — catches frozen game windows that transport-level keepalive misses.
5. `disconnect(client_id)` for any `Outcome::Disconnect`.
6. Broadcast `Position` on channel 1 to each ready client (slice 1 has one player; broadcasts as echo. Real fan-out lands with AOI).
7. Periodic 60s checkpoint pass — single SqliteUPDATE per dirty row.
8. `transport.send_packets(&mut server)` — push outbound.

`tokio::time::interval` with `MissedTickBehavior::Delay` keeps the cadence sane after a slow DB await (which only happens on Connect or 60s checkpoint).

Server-authoritative speed cap: `MAX_MOVE_SPEED = 7.5 m/s` × `TICK_DT = 0.05 s` = `0.375 m/tick` max displacement. Move intents are clamped via `Vec3f::clamp_length(1.0)` before scaling — client can't cheat by sending direction vectors longer than 1.

Out-of-order Move packets (unreliable channel can reorder) get dropped via `last_move_seq` comparison.
