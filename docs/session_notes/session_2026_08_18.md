## 3. The real find: inventory desyncs and cannot recover until relog

The tester's free-text note was the valuable part of the run:

> *"From time to time items seem to get hung up. Some seem to stick to the cursor while others will
> stick in the slot... Water Flasks vanished from the inventory then reappeared after i placed the
> stack of bread loaf on top of what appeared to be an empty slot."*

The attached server log says exactly what is happening. Across 16:03 to 16:33:

```
16:29:48  MoveItem rejected src_slot=2 dst=bag_0/2  error=source slot empty
16:29:50  MoveItem rejected src_slot=1 dst=bag_0/0  error=source slot empty
16:29:52  MoveItem rejected src_slot=5 dst=bag_3/0  error=source slot empty
16:29:54  MoveItem rejected src_slot=4 dst=bag_3/1  error=source slot empty
```

Dozens of them, repeatedly on the same base slots (1, 2, 4, 5), over half an hour. **The client
believed those slots held items; the server knew they were empty.** The server was right the whole
time. Nothing was lost. The relog at 16:37 resynced, and moves worked normally afterward.

### Two faults compound, and neither side can correct the other

- **Server: a rejected `MoveItem` tells the client nothing.** `world/tick.rs:5302-5313` logs the
  rejection and `continue`s. No corrective delta, no rejection message. The client never learns its
  view is wrong, so it retries the same impossible move indefinitely. The
  `if touched.is_empty() { continue }` immediately below has the same shape.
- **Client: a `bag_<i>` delta is silently discarded.** `autoloads/inventory.gd`'s `bag_` branch
  returns early when `bag_contents[i] == null`, with a comment relying on *"the next snapshot"* to
  resync. There is no periodic snapshot; the only one is at enter-world. So the dropped update is
  permanent.

One side throws information away and the other refuses to send it. That is why a divergence, once
started, survives until relog.

### Ruled out

- **Not packet loss.** `CHANNEL_SYSTEM` is `SendType::ReliableOrdered` with a 150 ms resend, so
  deltas are not dropped in transit.
- **Not a timing race.** The retries are roughly 2 seconds apart, orders of magnitude beyond RTT.

### Why it *looks* like items vanishing rather than an error

Two pre-existing UI behaviours make a desync read as data loss:

- `_refresh_cell` paints a cell **empty** while it is the drag source (`is_drag_source`), so a
  stuck drag makes the item disappear from its slot even though the data still holds it. That is
  the vanishing Water Flask. Dropping bread loaf on the slot forced deltas that repainted it, which
  is why the flask "came back".
- Right-click is deliberately a no-op while a drag is active (`inventory_window.gd:340`), which is
  why a bag "won't open" in that state.

### Not caused by the bag change

Worth stating plainly, since it surfaced during the bag playtest. Both faults date to **May 2026**:
`2026-05-19` for the client silent-drop (`534cf97`, "Track 14.3 client + fixture: bag locations")
and `2026-05-22` for the server's silent rejection (`18ae60a`, "Track 15: server-authoritative
inventory finale"). Three months before the bag work.

What the bag fix did was make bags draggable for the first time, and this checklist then exercised
dragging harder than any previous session, in and out of bag windows. That is what surfaced a
latent bug, not what created it.

### Fix direction

Two halves, matching the two faults: make the server answer every rejected or no-op inventory
intent with the truth about the affected slots, and stop the client discarding deltas silently. A
client-only mitigation exists (re-request a snapshot after a suspicious rejection) but the server
half is the real fix, and it needs a push plus an R720 restart. Tracked as its own To-Do item under
Phase 3, which is where it belongs: nothing is lost, but it reads exactly like the game eating your
things.

# 4. Fixing the desync (same day)

Both halves built. Server `world/tick.rs` + client `autoloads/inventory.gd`. Playtest:
`inventory_desync_checklist.md`. Needs a server push + R720 restart **and** a client re-export.

## Server: say something when you refuse

New `correct_client_slots()` answers a rejected `MoveItem` with the true contents of both slots
the client named, using the existing `peek_at()` + `send_inventory_delta()` pair (the bank store
path already used that idiom). The `touched.is_empty()` no-op branch gets the same treatment,
since the client still moved something on its own screen to get there.

**Targeted deltas rather than a full `InventorySnapshot`, deliberately.** A snapshot would also
work and `send_inventory_snapshot()` already exists, but it hands a broken or hostile client a
cheap amplifier: one small bad request, one large response, repeatable as fast as it likes. Two
small messages per bad request is proportional, cannot amplify, and still converges, because the
divergence that matters is exactly the one the client just acted on.

## Client: stop throwing away the truth

The `bag_<i>` branch had **two** silent drops, not one: the known
`bag_contents[base_idx] == null`, and a second `slot >= arr.size()` a few lines below. Both now
make room and apply the delta, and log a `DebugLog.warn`. The server is authoritative; if it says
what is inside a bag, that bag exists, and our disagreement is the thing that is wrong. Needing
either path at all means the base slots were already stale, which is worth seeing rather than
hiding.

## A test that asserted the bug

`move_item_empty_source_drops_silently` failed immediately, and it deserved to: it asserted
*"MoveItem on empty source must not fan an InventoryDelta"* — the silent drop, written down as the
contract. Rewritten as `move_item_empty_source_corrects_client`, proving both named slots come
back corrected and both report empty.

This is the third time in two days that a written description encoded the wrong thing (after
"does not live-refresh" and "stale pre-grammar bags"), and the first time one was encoded in a
*test*, where it actively defended the bug against being fixed.
