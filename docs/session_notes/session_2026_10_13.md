## 3. The food branch review: one real hole, closed at creation

finding: `create_character` validated only the name, so a modified launcher could send
`race: "Revenant"` (the transformation has a stat block, and under the food model that

## 4. A harness walk that overshot: the pet-after-Gate test

The full suite on the hosting worktree, run after the food merge, failed one test,
`a_pet_stays_with_its_owner_after_gate`, at the step where the pet closes on the dummy;
the same test passed alone and had passed in the deploy-branch run minutes earlier. By the
project's rule a failure that passes alone is a timing race to find, not a flake to
tolerate, and this one is arithmetic rather than luck. The harness's `walk_dir` sends N
Moves fifty milliseconds apart and stops, but the server keeps integrating the held
direction for `STALE_MOVE_THRESHOLD` (500 ms) after the last Move it received, so a
"1.5 m" step runs about 5.25 m: the owner ends 2.25 m PAST the dummy with 2.7 m of
bare-handed reach, one tick to spare. Under the suite's load the five sends stretched,
the owner ran out of reach, the swing was a Miss, and the pet had no target to inherit.

Fixed in the harness, not the server (server `a7e0a85`, deploy branch, merged into
hosting as `64201c2`): a new helper `walk_until_within` aims each tick's Move at the
target from the newest own Position the server has fanned, and parks the mover with a
zero Move once that Position is inside the stop distance; an overshoot between two
Positions turns the next Move around, so the walk converges however long a sleep took.
`walk_dir` keeps its two callers (both walk AWAY from something) and its doc now says what
it really does. The deploy-branch world suite: 94 of 94.

## 5. A latency readout: `/ping` and the `player link` line

The user asked whether the work keeps latency in mind. The verified answer: the gameplay
paths carry deliberate margins (client-predicted movement blended toward the server with a
1 m snap threshold and a 500 ms hold on the last direction; remote entities drawn 100 ms
behind; a 100 ms early tolerance on the cast-time gate and a 2.25 s client global cooldown
against the server's 2.0 s; client ranges one metre tighter than the server's), the hosting
work adds TLS to the login handshake only, and three gaps are honest: no input replay (past
about 250 ms round trip the blend would show as rubber-banding), no hit lag compensation,
and no latency readout at all, so a tester on the public host could not report a number.
The user took the readout: "latency readout, great idea."

Built (server `a18e355`, client `f6aa0ff`): the wire layer exposes renet's own round trip and
packet-loss estimate for the world connection (`NetClient.rtt_ms`, `packet_loss`; renet
measures the round trip off the acks of the packets the game actually sends and smooths it
with each new sample weighing an eighth, so it is the UDP path play runs on, not an ICMP
ping); `Net.get_rtt_ms` and `get_packet_loss` call them BY NAME so a stale DLL costs the
command and not the autoload (the `time_of_day` rule); `/ping` (or `/latency`) prints
"Round trip to the server: N ms, packet loss N%." and says so when not in a world or when
the DLL predates it; and the server logs a `player link` line per player once a minute
(char_id, name, rtt_ms, packet_loss) beside the enemy position fan line, so the operator's
log carries the same figure. A new headless check, `tools/check_wire_layer.gd`, prints which
by-name signals and methods the checkout's DLL is missing, for the stale-DLL hazard the
build stamp only fingerprints. The DLL was rebuilt and copied into the addon; the export
must take it (the Oct 22 export already carries a DLL rebuild for the trade window's bump).
The tester README's bug-report list gains "if it felt laggy, type /ping", and the hosting
checklist's hotspot section a row for it. The server half rides the next redeploy.
