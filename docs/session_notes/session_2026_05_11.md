## Sub-task 1 — Wire format: EntitySpawn variant + race/class load

**Protocol bump.** Added `EntitySpawn { id, name, race, class, level,
pos, yaw }` variant to `ServerWorldMsg` in `crates/protocol/src/world.rs`,
placed after `EntityDespawn` so the bincode discriminant order stays
append-only. `WORLD_PROTOCOL_ID` bumped from `PD_W0001` → `PD_W0002`
(`0x5044_5f57_3030_3031` → `0x5044_5f57_3030_3032`). Auth-minted
ConnectTokens are signed with this id; mismatch ⇒ token rejected at
the renet handshake.

Important post-hoc finding: the protocol-id check is **server-side
only**. The token has the id embedded (signed by the server's
netcode private key); the client just relays the opaque token to
the netcode transport, never compares against a local constant.
So an exported `.exe` built against PD_W0001 still **connects** to a
PD_W0002 server — the rejection point is the token signature check,
which always uses the server's current constant. Practically this
meant the user's pre-Track-3 game export connected successfully to
the new server but had no Track-3 GDScript or new signals; surfaced
as "everything looks fine in the server log, but the clients don't
render each other." Fix was re-export. The constant bump remains
correct for the future case where a client mints its own tokens or
checks the id locally; it just doesn't act as a kill-switch right
now.

**Server: race/class load.** `CharacterSpawn` and `SpawnRow` in
`crates/projectdawn-server/src/db/mod.rs` gained `race: String` and
`class: String` fields; the `SELECT` in `load_character` was extended
to include them (the columns have existed in `0001_init.sql` from day
one, just unread). `PerConnection` in `world/connection.rs` got the
same two fields, populated by `from_spawn`. Fields stay
`#[allow(dead_code)]` until the next sub-task reads them.

**GDScript mirror.** `SW_ENTITY_SPAWN := "EntitySpawn"` added to
`scripts/net/protocol.gd` in both the game and launcher repos in the
same commit pair; SHA256 of the two files matches post-edit (1:1
invariant preserved).

`cargo test --release` 6/6 passing. Server commit `d2ac25d`; game
mirror `a1006c4`; launcher mirror `d2f8a4e`.

## Sub-task 3 — Server-side fan-out (EntitySpawn / Position / EntityDespawn)

The biggest server-side change of the track. Three places touched.

**Connection lifecycle ordering.** The handoff sketch initially put
EntitySpawn fan-out in `tick.rs`'s `ServerEvent::ClientConnected`
arm, but at transport-connect time the new client's `ready` flag is
still false (it flips in the app-layer `Connect` arm in
`handlers.rs`). Identity isn't settled until app-Connect; the only
correct broadcast point is there. Implemented by adding a new
`Outcome::JustConnected` variant returned from `handle_message` when
`conn.ready` transitions false → true. `tick.rs` tracks a
`newly_connected: Vec<ClientId>` list during the message-drain phase
and runs the fan-out as a new step 4a (between disconnect drain and
movement integration):

```rust
for new_id in &newly_connected {
    if to_disconnect.contains(new_id) { continue; }
    if !connections.contains_key(new_id) { continue; }
    let peer_ids: Vec<ClientId> = connections.iter()
        .filter(|(id, c)| *id != new_id && c.ready)
        .map(|(id, _)| *id)
        .collect();
    // New client → existing peers
    if let Some(new_conn) = connections.get(new_id) {
        for peer_id in &peer_ids {
            handlers::send_entity_spawn(&mut server, *peer_id, new_conn);
        }
    }
    // Existing peers → new client
    for peer_id in &peer_ids {
        if let Some(peer_conn) = connections.get(peer_id) {
            handlers::send_entity_spawn(&mut server, *new_id, peer_conn);
        }
    }
}
```

The `to_disconnect.contains(new_id)` skip handles the rare case
where a client both connects and gets kicked in the same tick (e.g.,
a duplicate-Connect that fails validation on the second one) — no
point spamming a spawn the peers would immediately despawn.

**Despawn fan-out** in `ServerEvent::ClientDisconnected`: broadcasts
`EntityDespawn { id: leaver.char_id }` to every other ready peer
**before** removing the leaver's `PerConnection` from the map. Gated
on the leaver having been `ready` (no EntitySpawn was ever sent for
unready clients, so a matching despawn would land at peers who
never had a record of them).

**Position fan-out.** Step 6 in `tick.rs` was previously a per-client
echo-to-self (`broadcast_position(server, client_id, conn)`). Now a
true fan-out: every ready client's position to every ready client
INCLUDING themselves (Track 2's snap-or-lerp depends on the owner
receiving own broadcasts to drive reconciliation). Encode each
sender's Position once, clone bytes per recipient. At
MAX_CLIENTS=64 and ~50 B per Position the worst-case memcpy is
64×64×50 = 200 KB/tick ≈ 4 MB/s — trivial.

**handlers.rs refactor.** `send_position` factored into
`build_position_msg(conn) -> Option<Vec<u8>>` (pure encode) plus a
thin sender; `broadcast_position` wrapper deleted (single caller
migrated to the fan-out loop). Added `send_entity_spawn(server,
recipient_id, conn)` and `send_entity_despawn(server, recipient_id,
entity_id)` — both go on the reliable system channel so critical
state changes can't ride the unreliable Position channel.

**AOI strategy** per handoff open question 1 (user-confirmed): no
spatial filter, "everyone in the zone sees everyone." Pre-Steam
alpha at MAX_CLIENTS=64 is comfortably under any meaningful
threshold; spatial AOI (grid hash, octree) is a future track when
populations grow.

**Two-client integration test.** New
`crates/projectdawn-server/tests/world_two_clients.rs` (~280 lines,
adapted from `world_smoke.rs`). Brings up two independent renet
clients against an in-process auth+world, asserts:

1. After both app-connect, A receives `EntitySpawn{id=B}` with
   name/race/class/level intact and B receives `EntitySpawn{id=A}`.
2. After both send Move, each receives a `Position` broadcast
   carrying the **other's** id.
3. After B sends app-Disconnect, A receives
   `EntityDespawn{id=B.char_id}`.

Test suite now 7/7 passing. The asymmetric-visibility bug surfaced
in sub-task 5's manual test (lobby vs world scene) was invisible
here because the integration test drives raw renet clients with no
Godot scene tree — confirming we need both kinds of verification.

**Clippy bump.** The new `entity_spawn` signal has 7 identity fields
by design; `#[godot_api]` expands the declaration into an 8-arg fn
(with self), tripping clippy's default 7-arg threshold at the macro
invocation line where item-level `#[allow]` attributes don't reach.
Suppressed with crate-level `#![allow(clippy::too_many_arguments)]`
at the top of `crates/gdext-net/src/lib.rs` with a comment explaining
the macro expansion. `cargo clippy --workspace --all-targets`
clean post-fix.

Server commit `fb95bbb`.

## Sub-task 4 — Client: Net signal re-emit, remote_player scene, manager

Three pieces, two commits.

**Piece A — `autoloads/net.gd` signal re-emit.** Two new coarse
signals:

```gdscript
signal world_entity_spawn(
    id: int, player_name: String, race: String,
    char_class: String, level: int, pos: Vector3, yaw: float)
signal world_entity_despawn(id: int)
```

`_ready()` connects `entity_spawn` / `entity_despawn` from the
GDExtension; handlers re-emit on the autoload-level signals. Two
parameter renames on the receiver side: `name` → `n` (would shadow
`Node.name`) and `class` → `char_class` (GDScript reserved word).
The outbound signal carries `char_class` so downstream consumers
use a non-reserved name throughout. Project_Dawn commit `b26baab`.

**Piece B — `scenes/remote_player.tscn` + `scripts/remote_player.gd`.**
New scene: `CharacterBody3D` (matches local player's node type for
future doorway/push behaviour) + `CapsuleMesh` (2.0 m × 0.4 m,
matches `player.tscn`) + billboarded `Label3D` (font 36, outline 8,
no depth test, y=2.2 to clear capsule top). No `Camera3D`, no input
handling, no `_input` / `_unhandled_input`. The new script
`class_name RemotePlayer` carries:

- Identity fields (`char_id`, `player_name`, `race`, `player_class`,
  `level`) set by the manager before `add_child` fires `_ready`,
  so `_ready` can read `player_name` and stuff it into `NameLabel.text`.
- Snapshot-interpolation buffer (`BUFFER_CAPACITY = 5`) of
  `{ time, pos, yaw }` dicts ordered by time.
- `on_position_update(pos, yaw, sequence)` — drops sequence-≤-last
  (unreliable-channel reorder/dupe), appends snapshot, evicts oldest.
- `_physics_process` renders at `now − INTERP_LAG` (100 ms per
  handoff open question 2, user-confirmed). Always interpolates
  between two snapshots in the past, never extrapolates into the
  future. Linear search through the 5-slot buffer for the
  straddling pair; degenerate-zero-span snapshot pair snaps to the
  newer entry.

**Piece C — `autoloads/remote_player_manager.gd`.** Listens to
`Net.world_entity_spawn` / `world_entity_despawn` / `world_position`,
manages `Dictionary[char_id → RemotePlayer]`. Filters own-player on
every signal (`id == Net.get_player_id()` → skip). Registered in
`project.godot` as the last autoload (after `Net`, so `Net._ready`
runs first and its signals are defined when the manager connects to
them).

Sub-task 4 originally shipped with `_add_to_active_scene(rp)`
parenting RemotePlayers under `get_tree().current_scene`. That
worked for the integration test (no Godot scene tree) and for the
local-save F5 smoke test (no remote players to surface anything).
The bug only surfaced in the multi-instance manual test — see
sub-task 5.

Project_Dawn commit `7faceef`.

## Sub-task 5 — Two-instance verification (and the lobby-scene fix)

User ran the manual verification. Both `.exe` instances connected to
the server cleanly per `server.log`. Initial result:

- Character A (first-joined): saw Character B render and move.
- Character B (second-joined): did **not** see A. Clean server log,
  no errors anywhere.
- Enemy spawns desynced between the two clients — expected (enemies
  are client-local with independent RNG; not part of Track 3).

**Root cause: lobby vs world scene parenting.**

When B completes the app-layer `Connect` handshake, the server's
fan-out fires `EntitySpawn(A) → B` on the reliable system channel
immediately. But B is still on the launcher's lobby scene at that
moment — `Net.app_connected` just fired, surfacing the "Enter World"
button; B hasn't clicked it yet. The original `RemotePlayerManager`
parented the new RemotePlayer node under `get_tree().current_scene`
— the lobby — and when B clicked Enter World, the lobby was freed
along with our RemotePlayer for A. Server doesn't re-send EntitySpawn
(it's a one-shot reliable message), so B was left in world.tscn with
no record of A. Subsequent `Position` broadcasts for A arrived but
got dropped by the manager's "position before spawn" defensive
branch (`_by_id.get(id) == null`).

A didn't hit this because by the time B connected, A was already in
world.tscn, so A's RemotePlayer(B) parented to a stable 3D scene.

The integration test passed both directions because it drives raw
renet clients with no Godot scene tree — exposing the gap between
"works at the wire" and "works at the engine."

**Fix.** Split state into two maps:

- `_spawn_data[id]` — last known identity + spawn pose per char_id.
  Autoload-scoped; survives scene swaps. Source of truth for
  rehydration.
- `_by_id[id]` — live RemotePlayer node per char_id. Scene-scoped
  (parented under the current scene's root); freed automatically on
  scene transition.

`_process` polls `get_tree().current_scene`. On scene swap, drops
`_by_id` (nodes died with the previous scene) and queues a
`_needs_rehydrate` flag. The rehydrate fires only into a scene that
hosts the local player (membership in the `player` group — set by
`player.gd._ready` via `add_to_group("player")`), naturally gating
on world.tscn without hard-coding a scene path. The flag persists
across frames so the local player joining its group one tick after
the new scene becomes current doesn't fall through the cracks.

`_on_entity_spawn` always caches into `_spawn_data` and instantiates
only if the current scene hosts the player; otherwise the rehydrate
loop catches up on the next world entry. `_on_entity_despawn` removes
from both maps. `_on_position` updates the live node if it exists
(drops otherwise — covers both channel-race and lobby-pending cases).

Re-test by the user: both clients see each other regardless of join
order. Walking is smooth (user: "Could be smoother, but it's good
for now"). Closing one window despawns the capsule + nameplate on
the other "immediately" (within one server tick).

Project_Dawn commit `108bcf6`.

## Pending / deferred

- **Enemy spawn synchronisation.** Mobs spawn locally on each client
  with independent RNG; they desync immediately. Out of Track 3
  scope. Future tracks need server-authoritative enemy state
  (likely Track 5 or 6) — at minimum the spawn point + respawn
  timer state has to live server-side and broadcast as another
  `EntitySpawn` / `EntityDespawn` flavour.
- **Yaw replication.** Remote players interpolate yaw between
  `Position` broadcasts, but the local player doesn't currently
  send yaw in `Move` (the server has `conn.yaw` from
  `load_character` and never updates it from intent). Visible
  artifact: remote-player capsules face their last login yaw and
  don't turn while walking. Easy follow-up — add yaw to `Move` and
  store on `PerConnection` in the Move handler.

  issue that throws in PowerShell 5.1 on line 16 (`throw "$serverDir
  — ..."`). Ran inline cargo + Copy-Item during this session. One-line
  fix; deferred.
- **Walking smoothness.** User accepted as "good for now" but flagged
  room for improvement. Likely tunable via INTERP_LAG (currently
  100 ms) and the snapshot-pair search (linear; could be the latest
  pair always if we trust monotone timestamps). Re-tune once the
  yaw + animation work lands and the visual feel can be judged
  end-to-end.
- **WORLD_PROTOCOL_ID enforcement.** Today the constant lives in
  the auth-server's token mint and the server's token check; the

  PD_W0001 still hand-off and connect against a PD_W0002 server.

- **Re-export reminder.** The user's first multi-instance test
  used the pre-Track-3 `builds/ProjectDawn.console.exe`, which
