# Session 2026-08-14 — `/testpanel`, GM state from the handshake, and a build stamp

A short session with a disproportionately useful lesson in it. Commits: client `cc1e203`,
`e1792c3`, `68377bf`; server `0ff0387` (wire **PD_W0026**).

---

## 1. `/testpanel` (alias `/gm`)

The Test Panel had no way to be opened or closed once the hosted server stopped granting dev
commands to everyone. Started as a hotkey; changed to a chat command instead, deliberately, so
it costs no keybind. `/testpanel` toggles the panel, and mounts it on demand if it was never
instantiated (`e1792c3`).

When it refuses, it now **says why**, naming the deciding flags. That diagnostic is what solved
the next problem.

---

## 2. The GM bug: same account, two characters, different answers

Account `tailscale` had `is_gm=1`. Character **Pockets** had Test Panel access. Character
**plump**, on the same account, did not.

### Three wrong guesses first

Worth writing down, because all three were plausible and all three were wrong:

1. *"plump is on a different account."* Disproved by the DB: both characters, `account_id=1`,
   `is_gm=1`.
2. *"GM was granted mid-session, so plump's session predates it."* Disproved by the user: GM had
   been on that account for days before plump was even created.
3. *"You're running the stale `ProjectDawn-alpha` executable."* Disproved by a screenshot showing
   the new diagnostic text, which only the new build could print.

The lesson is the ordinary one: each guess explained the symptom, and none of them was checked
against evidence before being offered. The fix arrived only once the client was made to *report*
its own state.

### The actual root cause was structural

The diagnostic printed `GM: no, hosted session: yes` at the same moment the server log said
`GM account connected`. Client and server disagreed about the same fact.

The client cached `is_gm` from the **auth** `LoginOk` message, which is only handled in
`login.gd`. Any route into the world that does not pass through the login screen therefore
leaves the flag at its default `false`. It was never about the character or the account; it was
about which path that particular session took to get in.

### The fix

Move the fact to a message every session receives, regardless of path. `ConnectOk` (the **world**
handshake) now carries `is_gm`, bumping the wire protocol to **PD_W0026**
(`WORLD_PROTOCOL_ID = 0x5044_5f57_3030_3236`). `Net._on_connect_ok` assigns it directly:

```gdscript
_is_gm = is_gm_flag     # PD_W0026: authoritative, path-independent
```

The auth-side flag is no longer the source of truth. Confirmed working: "`/testpanel` opens/closes
the test panel."

## 3. Build stamp on the boot line

Guess 3 above cost real time because there was no way to tell, from the outside, which build the
R720 was actually running. There is now.

A `build.rs` in `projectdawn-server` stamps `PD_BUILD_COMMIT` (short sha, plus `-dirty` when the
tree is modified), with `rerun-if-changed` on `.git/HEAD` and `.git/index`. `main.rs` prints it
on the boot `tracing::info!` line alongside `dev_cmds`:

```
build="0ff0387" dev_cmds=false
```

Two fields, both worth checking after every restart: one says whether the deploy is current, the
other says whether every connected player has `/give`.

The client had no equivalent at this point. That gap is closed below.

## 4. The client build stamp

Same problem, harder mechanics: Godot has no `build.rs`. The requirement was explicit, and it is
the whole design constraint: *a stamp you have to remember to update will go stale, and a stale
stamp is worse than none because it is believed.*

**Mechanism.** A new `addons/build_stamp` registers an `EditorExportPlugin`. In `_export_begin()`
it shells out to git and injects `res://generated/build_stamp.json` straight into the PCK with
`add_file()`. **Exporting is the stamping step**, so there is no second action to forget.

Every on-disk alternative was rejected for reintroducing exactly the staleness being eliminated: a
generated-and-gitignored file is absent on a fresh clone; a generated-and-tracked file churns every
build and can be committed stale; and either way it is produced by a step ordered independently of
the export. `add_file()` leaves **no on-disk artifact at all**, verified after the export run: no
`generated/` directory exists in the working tree.

**Verified rather than assumed**, since guessing a Godot API costs an export cycle to discover:
- `_export_begin` files land in the pack, ahead of per-file iteration.
- They survive this project's `script_export_mode=2` (compressed binary tokens).
- `.git/` is **not** shipped in an export, so a runtime git read is dead in a tester build. This is
  the whole reason an export plugin is required rather than reading git at startup.
- A real headless export printed `[BuildStamp] stamped 09ad51e DIRTY TREE`, matching
  `git rev-parse --short HEAD` exactly.
- The editor fallback returned `09ad51e-dirty-dev` on branch `fix/xp-leveling-overflow`.

### The bug that adversarial review caught

The first proposal was `OS.execute("git", ["rev-parse", "--short", "HEAD"], out, true)`. That
inherits the **calling process's working directory**. This is a two-repo project, and an editor
launched from a shell sitting in `F:\Projects\server` would have stamped **the server's commit into
the client**: well-formed, plausible, wrong, and unfalsifiable from a screenshot. Precisely the
failure the stamp exists to prevent.

Every git call now passes `-C <project root>` from `ProjectSettings.globalize_path("res://")`, and
cross-checks `rev-parse --show-toplevel` against that root before trusting the result. Path
comparison is normalized, because `globalize_path` returns `F:/...` while git may return a
different drive-letter case, which would otherwise fail the check on every export.

### Other hardening

- **Dirty is computed with `--untracked-files=no`.** Untracked files are this repo's normal state
  (`docs/deployment/` is deliberately uncommitted, `.uid` files come and go). Counting them makes
  every build "dirty" and the flag carries zero information: 6 changes naive, 2 real.
- **Failure is loud, never plausible.** Git failure writes a literal `UNSTAMPED`, never a blank or
  a last-known value. A template build with no stamp at all renders **red `UNSTAMPED BUILD`** on
  the login screen, because that means the addon is disabled, and Godot silently disables an addon
  whose script fails to load.
- **`gdext_net.dll` is fingerprinted separately** (md5 + size). It is gitignored and hand-copied
  into `builds/`, so it is invisible to the commit sha, yet it implements the wire protocol. A
  "clean" client can otherwise ship a stale wire layer that presents as a server bug.
- **An export timestamp and branch/unpushed count** are recorded. A sha alone cannot answer "did
  you install the build I sent an hour ago?", since two exports of one commit are identical under a
  hash-only stamp.
- **`_rotate()` re-stamps.** The build line is written at session start, so without this a session
  long enough to rotate (2000 lines, ordinary in a playtest) would hand us an unidentifiable log.

**Surfaces:** login screen bottom-right (short sha), `debug.log` header and rotation banner (full
one-line detail), and `/version` (alias `/build`), which is deliberately **not** GM-gated since the
entire point is asking a tester to read it back.

**Do not put a git sha in `application/config/version`.** The Windows exporter falls back to that
key for the .exe file-version resource, rejects non-numeric values, and silently substitutes
`1.0.0.0`.

## Deployment gotchas found the hard way

Both belong to the R720 update sequence and both fail *silently*, which is what makes them worth
recording:

- **`sudo -u projectdawn bash -c '...'` does not find `cargo`.** A non-interactive shell skips
  `~/.cargo/env`, so the build never ran and the subsequent `cp` happily copied the previous
  day's binary. Use `sudo -u projectdawn -H bash` (an interactive login shell) instead.
- **`cp` onto the running binary fails with `Text file busy`.** `systemctl stop` first, then
  copy, then start.
