# Session 2026-08-14 — `/testpanel`, GM state from the handshake, and a build stamp

A short session with a disproportionately useful lesson in it. Commits: client `cc1e203`,
`e1792c3`, `68377bf`; server `0ff0387` (wire **PD_W0026**).

---

## 1. `/testpanel` (alias `/gm`)

The Test Panel had no way to be opened or closed once the hosted server stopped granting dev
commands to everyone. Started as a hotkey; changed to a chat command instead, deliberately, so
it costs no keybind. `/testpanel` toggles the panel, and mounts it on demand if it was never
instantiated (`e1792c3`).

When it refuses, it now **says why**, naming the deciding flags. That diagnostic is what solved
the next problem.

---

## 2. The GM bug: same account, two characters, different answers

Account `tailscale` had `is_gm=1`. Character **Pockets** had Test Panel access. Character
**plump**, on the same account, did not.

### Three wrong guesses first

Worth writing down, because all three were plausible and all three were wrong:

1. *"plump is on a different account."* Disproved by the DB: both characters, `account_id=1`,
   `is_gm=1`.
2. *"GM was granted mid-session, so plump's session predates it."* Disproved by the user: GM had
   been on that account for days before plump was even created.
3. *"You're running the stale `ProjectDawn-alpha` executable."* Disproved by a screenshot showing
   the new diagnostic text, which only the new build could print.

The lesson is the ordinary one: each guess explained the symptom, and none of them was checked
against evidence before being offered. The fix arrived only once the client was made to *report*
its own state.

### The actual root cause was structural

The diagnostic printed `GM: no, hosted session: yes` at the same moment the server log said
`GM account connected`. Client and server disagreed about the same fact.

The client cached `is_gm` from the **auth** `LoginOk` message, which is only handled in
`login.gd`. Any route into the world that does not pass through the login screen therefore
leaves the flag at its default `false`. It was never about the character or the account; it was
about which path that particular session took to get in.

### The fix

Move the fact to a message every session receives, regardless of path. `ConnectOk` (the **world**
handshake) now carries `is_gm`, bumping the wire protocol to **PD_W0026**
(`WORLD_PROTOCOL_ID = 0x5044_5f57_3030_3236`). `Net._on_connect_ok` assigns it directly:

```gdscript
_is_gm = is_gm_flag     # PD_W0026: authoritative, path-independent
```

The auth-side flag is no longer the source of truth. Confirmed working: "`/testpanel` opens/closes
the test panel."

## 3. Build stamp on the boot line

Guess 3 above cost real time because there was no way to tell, from the outside, which build the
R720 was actually running. There is now.

A `build.rs` in `projectdawn-server` stamps `PD_BUILD_COMMIT` (short sha, plus `-dirty` when the
tree is modified), with `rerun-if-changed` on `.git/HEAD` and `.git/index`. `main.rs` prints it
on the boot `tracing::info!` line alongside `dev_cmds`:

```
build="0ff0387" dev_cmds=false
```

Two fields, both worth checking after every restart: one says whether the deploy is current, the
other says whether every connected player has `/give`.

**The client still has no equivalent.** Testers run whatever executable they last received, and
there is no way to read its version from a screenshot. Worth adding.

## Deployment gotchas found the hard way

Both belong to the R720 update sequence and both fail *silently*, which is what makes them worth
recording:

- **`sudo -u projectdawn bash -c '...'` does not find `cargo`.** A non-interactive shell skips
  `~/.cargo/env`, so the build never ran and the subsequent `cp` happily copied the previous
  day's binary. Use `sudo -u projectdawn -H bash` (an interactive login shell) instead.
- **`cp` onto the running binary fails with `Text file busy`.** `systemctl stop` first, then
  copy, then start.
