## 1. Server-driven time of day

Reported 2026-08-14: no two players shared a sky. `autoloads/time_of_day.gd` started at 8 AM
whenever the game process launched and ran from there, so two friends who started an hour apart
stood in different parts of the day. `ServerWorldMsg::TimeOfDay { hour }` had been in the
protocol all along with nothing sending it and nothing reading it.

**Server** (`e8164b1`). New `world/clock.rs`: the hour is derived from the wall clock over a
20-minute day (`hour_at(unix_secs)`), not counted up from boot. That one choice gives a shared
hour, a day that survives a restart, and nothing to persist. `fan_out_time_of_day` sends it to
each player in the EnterWorld seed block and to everyone once a minute (`BROADCAST_INTERVAL`,
step 7-ter of the tick), on the reliable channel. Nothing on the server reads the hour.

**Wire layer** (same commit, `crates/gdext-net`). One `Incoming::TimeOfDay` arm, one emit, a
`time_of_day(hour)` signal. No protocol bump. A client built before this routes the message to
`unhandled_server_message`, which nothing listens to, so the server half is safe to deploy
ahead of the export (checked in the client source, not assumed).

**Client.** `Net` re-emits `world_time_of_day`. `TimeOfDay` becomes a follower: a difference of
more than one game hour is a jump (the first send after login, when the world is still
loading); anything smaller becomes a correction worked off by running the clock up to 4x fast
or down to a quarter speed, never backwards, so the sun does not step once a minute. The
shortest-way-round arithmetic treats 23:50 told 00:10 as twenty minutes behind. Paused (the
Test Panel) ignores the server, and a paused clock now still paints, so "Pause, then drag the
slider" holds a hand-set sky online; unpaused it rejoins the server at the next send.

`Net` connects the new signal by name behind `has_signal`. Its neighbours use bare
identifiers, which are a parse error against a DLL that lacks the signal, and a parse error in
`net.gd` takes the whole autoload down. A stale DLL now costs the shared sky and logs an error
instead of costing the client.

**Lockstep to remember:** the day length lives on both sides (`DAY_LENGTH_SECS` in `clock.rs`,
`DAY_DURATION` in `time_of_day.gd`, 1200 s). CLAUDE.md's known-drift list says so.

**Exploit lens.** Server to client only; no server rule reads the hour; night vision
(`vision_system.gd`) is a client-side brightness and tint. A modified client could always
paint its own sky and still can; nothing depends on it.

### Verified

- Unit: four tests on the clock math (midnight wrap, an hour is a 24th of the day, the hour
  stays inside `[0, 24)` at the f32 boundary, two immediate reads agree).
- Integration: `every_player_is_told_the_same_hour_on_entering_the_world` (two players, the
  second joining late, each told the hour at once and told the same one).
- Headless probe, 22 checks, driven by emitting the DLL's own `time_of_day` signal so the
  whole client chain runs: snap, catch-up at no more than 4x, slow-down never negative, the
  midnight wrap, pause, non-finite and out-of-range hours.
- Full server suite: 249 unit, 66 integration, three consecutive green runs. Trade branch
  merged up (`3fbb810`; one keep-both conflict in `handlers.rs`), 254 unit and 69 integration.
- Not provable here: a real DLL decoding a real server's message in a running client. The
  arm is a copy of `Teleport`'s. `time_of_day_checklist.md` is the proof.

## 2. A trap found on the way: the addon DLL was the trade build

`addons/gdext_net/gdext_net.dll` was dated 09-29 and contained the trade window's symbols: it
was the PD_W0028 build left in place by the trade work, while the client tree sat on the

Today's rebuild from the deploy branch replaces it (verified: no trade symbols, has the clock
signal). Two things follow:

- The export must hand-copy `addons/gdext_net/gdext_net.dll` into `builds/`; the checklist

- **On trade deploy day the DLL must be rebuilt from `feat/trade-window`**, and rebuilt again
  from the deploy branch if work returns there first. The build stamp fingerprints the addon
  DLL, so `/version` will show which one a build carries; it cannot stop the wrong one being
  built in.

## 3. A test of mine that broke its own rule

`owner_keeps_seeing_a_pet_parked_two_cells_away` (written 10-02) failed once in today's full
parallel run and passed alone. It gave the pet a 10-second wall-clock deadline to cover 20 m
and waited a fixed 1.5 s for a 500 ms keepalive: distance and cadence against a clock, which
is exactly what the harness notes say never to do. Both waits now end on the observable effect
(the pet has set off toward its owner; a keepalive has arrived) with generous deadlines. The
first assertion, the one that fails on the old server code, is unchanged.

## 4. Bind and Gate: the design doc

`docs/design/bind_and_gate.md`, in the shape of the trade window design: what is broken,
reference behavior, what exists, the design, an exploit ledger that doubles as the test list,
and six decisions for the user with recommendations. No code.

What the reading turned up:

- **The client acts on its own.** `spells.gd::_apply_spell` sends the cast to the server and,
  in the same function with no online guard, runs `_execute_port` and `_execute_bind`. So
  online today Gate calls `ZoneLoader.travel_to` and reloads the whole world scene (the server
  never moved anyone and puts you back), and Bind Affinity prints "You are now bound to ..."
  beside the server's "That magic has no effect here yet."
- **Gate is not in `spells.toml` at all**; Bind Affinity is, with no arm.
- **No wire change is needed**, against the To-Do's expectation. The server can move a living
  player with the `Teleport` message Respawn and resurrection already use, and confirm a bind
  with a chat line. Slice 1 is a redeploy plus an ordinary export, and does not wait for the
  trade window's protocol bump.
- **Succor and Evacuate should wait.** Their numbers (level 12 and 16, 3 and 5 second casts,
  60 second cooldowns) are offline-era placeholders against EQ's level 57 and 9 seconds, and
  in a one-zone world the only safe point is the town, which makes Succor a better Gate than
  Gate.
- The recommended bind rule is a clearance, not a list of zones: not within 60 m of a hostile
  spawn point (the largest aggro radius today is 22 m, the largest default leash 44 m).

EQ rules were checked against the Project 1999 wiki and SWG's against the SWGANH wiki
(sources at the end of the doc), not written from memory.

## 5. Item three, scoped instead of built, and what the scoping found

The plan's third item was "`/camp` and a kick return you to character select". Reading the
flow showed it is not a small job: the session token and the auth socket live in the login
scene and die with a scene change, `Net.leave_session` leans on process exit to close the
socket, and 54 autoloads carry per-character state that a second character would inherit
unless each one is audited (the 08-26 hotbar bleed was exactly that). It needs a design pass
and a state-reset audit first. Not started; the To-Do entry now says why.

The same reading found something that did need fixing today. **When the world connection
ended in game, the client showed nothing.** `Net._on_kicked` logged an engine warning and
emitted `app_disconnected(reason)`; in the world scene the only listener was the camp label.
A kicked or dropped player stood in a frozen world with no explanation, and the 10-02 ban
kick, documented as telling the player why, did not on screen.

Built: `scripts/hud_disconnect_notice.gd`, in the `hud_*` component pattern, mounted by the
HUD. On `app_disconnected` the screen dims (and swallows clicks), a panel shows the server's
reason or a plain "The connection to the server was lost.", a hint about the relogin wait,
and a Quit button; the line also goes to chat and the debug log. Headless probe, 10 checks.
Rows added to `inspect_range_gm_audit_ban_checklist.md` §3, and the ban row now says what an
older client shows (nothing).

Also corrected in the To-Do: the "live relogin countdown" was filed as client-only because
the wire carries `reconnect_after_secs`. The DLL drops that field (the `kicked` signal passes
reason and code only), so it needs a wire-layer change and a rebuild.
