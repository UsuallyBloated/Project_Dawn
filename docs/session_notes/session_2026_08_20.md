## Three faults, two rounds, and the tester found the one that mattered

| # | Fault | Found | Effect |
|---|---|---|---|
| 1 | Server logged a rejected `MoveItem` and sent the client nothing | 08-18, from the log | a wrong client never learned it was wrong |
| 2 | Client silently discarded `bag_<i>` deltas it thought it had no home for | 08-18, reading the code | the server's truth was thrown away |
| 3 | **`Stack All` rewrote the whole inventory locally** | **08-20, by the tester** | one click made the client's entire view fiction |

Rounds 1 and 2 fixed *recovery*. The client could get back in step, but only one slot at a time,
as it happened to touch them. That is why the 08-20 checklist note read *"items stay vanished until
another item is placed into a particular slot"* — the correction working, reactively, against
something that kept re-breaking it.

Fault 3 was the thing re-breaking it, and the log alone would never have found it: a purely local
mutation leaves no server-side trace by definition. It took *"I believe the Stack All button might
be fucking something up."*

## Follow-ups from the same run

- **Food and water now stack to 20** (was 10), at the tester's request. Bread Loaf and Water Flask
  are the only food/drink items in the game, so that is the whole change. Made on **both** sides,
  since `stack_size` lives in the client `.tres` *and* the server's `items.toml` — the exact
  client/server drift CLAUDE.md warns about. Needs a server rebuild, because `items.toml` is
  compiled in via `include_str!`.
- **The uncapped server merge was caught in the wild:**
  `19:51:51 DestroyItem applied ... bread_loaf count=41`. A 41-stack of an item whose limit was 10,
  built by hand-merging, because the server's move-merge is a plain `saturating_add` with no
  capacity check. Stack All did not build it and cannot: it only pairs stacks that fit. That gap is
  its own open To-Do, and this log line is its evidence.
- **Stack All now lives only in the main inventory window.** The bag copy is gone. The action was
  always inventory-wide, so a button in each open bag implied a per-bag choice that never existed.

# Later the same day: cross-store transfers made atomic

Phase 3 was decided to run long rather than be cut short at its Aug 21 window, and the next item
taken was exploit-audit **finding 8**. Server-only; playtest `atomic_transfers_checklist.md`.

## An item never changes, it moves

That is the whole bug in one line. Every meaningful inventory action spans **two** tables:

| Action | Stores touched |
|---|---|
| Bank item deposit | `character_items` + `bank_items` |
| Bank coin deposit | wallet columns + bank columns |
| Vendor buy / sell | `character_items` + wallet |
| Death | `character_items` + wallet + `corpses` |

Each store had its own writer, each opening its own transaction, called one after another with an
`.await` in between. A crash landing in that gap leaves half the movement committed: the item is
either **gone** (left inventory, never arrived) or **duplicated** (arrived, still in inventory).

The dupe is the worse half. A loss gets reported by the player who suffered it; a dupe gets found
and quietly exploited.

## What changed

`db::save_stores_atomic()` writes inventory, wallet, bank coin, the personal vault and the shared
vault in **one** transaction, taking `Option` per store so only the dirty ones are touched. It
replaces the five separate writes in **both** places that had them:

- the periodic checkpoint (`persistence.rs`)
- the disconnect flush (`tick.rs`), which had the identical pattern and would have been easy to fix
  in only one place and call done

On success every covered flag clears together; clearing them individually would reopen the window.

## Death was the sharpest case

It wrote the corpse, then stripped the live player with two more separate writes:

```rust
let _ = db::save_inventory(&pool, cid, &[]).await;
let _ = db::save_coins(&pool, cid, protocol::world::Coins::ZERO).await;
```

Note the `let _ =`: failures were discarded entirely, not even logged. A crash between those two
statements leaves the corpse holding the coin **and** the player still holding it. That is a coin
duplication, on the most-travelled path in the game.

`save_corpse` now takes `strip_owner` and clears the owner's inventory and wallet inside the same
transaction that creates the corpse, so the two halves of the movement cannot separate. Either the
corpse exists and the player is empty, or neither happened and the death retries. The in-memory
state is then mirrored to match what already committed, and the dirty flags are cleared rather than
left for a checkpoint that has nothing left to write.

## Verification

- New unit test `save_corpse_strips_the_owner_in_the_same_transaction`: seeds gear and 1234 copper,
  kills, then asserts the corpse holds both **and** the character's inventory is empty and wallet is
  zero. It fails loudly on either half.
- 181 unit tests green.
- 41 of 42 integration; the one failure is `pet_pulls_aggro_via_threat_reaggro`, confirmed passing
  in isolation, one of the three documented flaky enemy-AI tests.

Worth being honest about what a playtest can show here: **nothing**, directly. The bug needs a crash
at a precise instant. The checklist therefore covers the ordinary paths, because breaking those is
the actual risk of a rewrite like this, and leaves the crash-correctness claim to the unit test.
