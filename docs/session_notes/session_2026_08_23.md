# Session 2026-08-23 — The refusal audit lands: batches 1 and 2, plus two real bugs

Server-only day: `7cc1bbc`, `f1aaf79`, `83d8e30`, deployed as `build="83d8e30"`. Follows directly
from the 08-21 finding that the vendor "eats" purchases with full bags.

---

## The audit

A three-agent workflow audited every intent handler on both sides of the wire. The headline:
**62 silent rejection arms against 40 that answer.** The server validates well but *reports*
poorly — it logs a refusal and `continue`s, telling the client nothing, so the client either keeps
a stale view (the 08-18 inventory desync) or announces a success that never happened (the vendor
bug).

The fix costs nothing to ship: `ChatMessage` on the System channel is already encoded, decoded by
gdext, and rendered unattributed by `CombatLog`, so `handlers::send_refusal()` needs no protocol
bump, no gdext rebuild, no client re-export. Two traps documented for whoever comes next:
`ServerWorldMsg::Error` and `BroadcastMessage` have **zero senders and no gdext decode** — building
on them would discard the reply silently, the very failure being fixed. And `fan_out_cast_fail`
broadcasts, so using it for refusals would leak a caster's failures to bystanders.

## Batch 1 (16 sites)

All 6 `BuyItem` arms, all 7 `SellItem` arms (the reported bug's twin — the client prints "Sold X
for N" with a locally computed price), and the three worst spell arms. The unknown-spell arm also
**refunds the mana** via `fan_out_mana_update`: the client spends mana before sending, so the ~32
client-only spells drained the bar for nothing in ordinary play.

## Batch 2 (36 sites total)

The inventory family (13 arms — `EquipItem` was the sharpest: the client speculatively unequips
the off-hand *before* a 2H equip, so a rejection left the player disarmed with nothing said), the
group ops (two `/kick` arms had **neither log nor reply** — invisible on both sides), and
`BindAtCurrentLocation`, highest consequence: the client printed "Your soul is bound to this
place." unconditionally, so binding as a corpse would silently rebuild the death loop. Both bind
branches now speak; the success had no confirmation message at all, which is why the client
guessed.

Deliberately left silent, confirmed correct: anti-cheat gates (a reply rewards the spammer),
dev/GM gates (a reply is an oracle for `PD_DEV_CMDS` / `is_gm`), transport/lifecycle gates, and
rejections only a forged client can reach.

## Two validate-after-mutate bugs, found by the audit and fixed

**Resurrection consumed the offer before validating.** A mismatched accept burned a good offer,
and a transient DB failure **ate an accepted resurrection** — the old comment conceded it
("the offer was already consumed above"). Now the offer is spent only on a decisive outcome;
a DB failure leaves it live and says "Try accepting again."

**Loot paid coin before checking the slot.** A bad slot index zeroed and credited the bag's coin,
then bailed silently. The bounds check moved above the payout.

Both are the same principle the atomic-store work established: validate before you mutate.

## The flaky-test rule was corrected

CLAUDE.md said three tests flake and "a failure outside those three is a real regression." Five
distinct tests failed under load in one sitting, each passing in isolation, on a clean tree too
(A/B proven). New rule: **any failure that reproduces in isolation is real; one that passes alone
is load-sensitivity, whichever test it is.** The old rule sent me chasing a phantom for ten
minutes and equally invites dismissing a real regression.

Suites ended the day 197 unit green and 42/42 integration — a fully clean run.
