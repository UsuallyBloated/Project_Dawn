## Task 1 — Drop an item to the ground
The whole drop path existed (`ClientWorldMsg::DropItem`, gdext `send_drop_item`,
`Net.broadcast_drop_item`, server spawns a **public** loot bag) but had **no UI caller**.
Per user direction, wired **two** gestures, both routing to `Net.broadcast_drop_item`:
- **Drop cell** — a new ⬇ cell beside the Trash cell in `inventory_window.gd`; drag an
  item onto it → confirm → drop. Mirrors the trash-cell pattern (`_make_drop_cell`,
  `_show_drop_confirm`, `_confirm_drop_to_ground`).
- **Drag out to world** — releasing a drag *outside* the inventory window (and outside the
  already-handled bag/paperdoll windows) now drops to the ground; releasing over the
  window's own chrome still snaps back. Hooks the existing `_input` drag-release fallback.

Both use a confirm dialog and **don't optimistically clear** — the server's
`InventoryDelta` empties the slot, mirroring loot pickup.

**Server (no wire change):** the `DropItem` apply handler only honored `location == "base"`
("non-base locations not yet supported") and called `drop_base`. Extended it to bag slots
by routing through the existing bag-aware `inventory.destroy_at(&location, slot, count)`
(same primitive the DestroyItem handler uses) + reading the post-state delta from base or
`bag_<i>`. Without this, dragging a *bag* item to the ground would have silently no-op'd.
- **Consolidation:** `destroy_at` now fully supersedes `drop_base` (identical base-slot
  semantics + bag support), so my change left `drop_base` dead → removed it and migrated
  its 5 unit tests to `destroy_at` (lib test count unchanged at 130).

## Task 2 — Defender sees incoming misses (PvP)
Pure client fix. The server already fans `Miss` to the defender (the PvP/out-of-range miss
paths fan to `in_world_recipients_now`, which includes every in-world player). The gap was
in `remote_player_manager.gd` `_on_miss`: it spawned the floating "miss" number but never
logged a combat-log line, unlike `_on_hit` which logs "X hits you". Added a symmetric
"X misses you." line on the `target == local player` branch, with a small
`_attacker_display_name` helper that mirrors `_on_hit`'s enemy-vs-peer name resolution.

## Task 3 — `/autosplit` toggle notifies the group
Needed a new server→client message + DLL rebuild. Added `ServerWorldMsg::GroupNotice
{ text }` (PD_W0014 append), a one-recipient `handlers::send_group_notice` (mirrors
`send_loot_rejected`), and routed the fan through the tick loop like the group intents: the
inline `SetAutosplit` handler now no-op-guards (only on an actual change) and returns
`Outcome::AutosplitNoticeIntent { char_id, on }`; a new drain loop (mirrors the 4hbb
loot-mode loop) looks up the toggler's group + name and fans "X set auto-split on/off." to
each **other** online group member. The toggler keeps their own local echo (`hud.gd`), so
they're excluded — no double-log; solo players fan nothing.

Bridge: gdext `group_notice(text)` signal + `Incoming::GroupNotice` decode/emit; `net.gd`
`world_group_notice` signal + `_on_group_notice`; `group_manager.gd` connects it and logs
via `CombatLog`. **gdext DLL rebuilt to PD_W0014** (4.01 MB).
