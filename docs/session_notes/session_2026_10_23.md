## 5. Phase 1, durability, built

After a pause the user said go, with two calls: build on the deploy branch (so the bump-day
restart and every one after it is already clean) and the EQ-flavoured line, "The world is
being restarted. Your progress has been saved; please log in again in a minute."

**Built** (server `b36904e` + review fixes `6c2bc45` on `fix/xp-leveling-overflow`, merged into
`feat/server-speed` as `a7a318f`; `phase1_durability_checklist.md`):
- **Graceful shutdown (M1).** `main` turns SIGTERM, Ctrl-C (and on Windows Ctrl-Break, a closed
  console, machine shutdown) into a watch channel the tick loop reads at the top of a tick. The
  loop saves everyone first, linkdead bodies and the retry queue included, retrying failures
  for 12 s inside systemd's 20 s; then each player is told the line that is true for them; then
  the kicks get five ticks to arrive and every connection is closed. Anyone unsaved makes the
  process exit non-zero. A second signal exits at once.
- **One save path.** `persistence::flush_connection` writes position, resources, the stores,
  skills, faction standings (on `feat/server-speed`) and quests, each clearing its flag only on
  success, and reports whether anything is left. The checkpoint, logout, the retry queue and
  shutdown all use it; the logout's hand-kept copy is gone, and so is the second copy of the
  quest flush and of the store-flag list.
- **The logout retry (M2).** A failed logout save queues the character, retried every second;
  the account's relogin is refused ("Your last session is still being saved") until it lands,
  and it is given up after 2 minutes (to the last saved state, which is whole, so a loss and
  never a dupe).
- **XP with its record (M3).** `db::XpProgress` is written inside the corpse, quest-completion
  and resurrected-flag transactions; `progression::progress_after` gives the numbers `award_xp`
  then lands on in memory. The resurrection refund had the same flaw and was folded in.
- **A dead world ends the process (M8).** The loop's error returns through `world::serve`.

**Review pass** (nine findings): telling players "saved" before saving and exiting 0 on a
failed save, the unbounded retry, the second Ctrl-C, the Windows console close, two stale
comments, the duplicated quest flush and store list, and the pending refusal's misleading
countdown, all fixed. One accepted residual, recorded: a character whose corpse save failed
(the database already failing) and who leaves before the retry is saved without its corpse.

**The merge into `feat/server-speed`** rebuilt `persistence.rs` by hand (git had interleaved a
faction save into the quest loop): alignment rides the resource save, faction standings are
part of the flush and of `has_unsaved_state`, the NO RENT logout stamp moved ahead of the
flush (so a queued departure is still stamped) and shutdown stamps everyone too.

**Tests**: a stop signal saves a walk and a purchase and tells both players; a failed logout
save (a test-only SQLite trigger) holds the relogin until the retry lands; a death's de-level
is in the database with the corpse; a quest's reward XP is in the database with the completion;
the resurrection refund is written with the flag (unit). Each integration test fails with its
fix disabled. Suites: deploy branch 290 unit and 111 integration, `feat/server-speed` 330 and
146, each green twice. The harness gained a stop signal, and a refused client now closes its
transport as the real client does (else its netcode slot blocked the next handshake).

  suite and `cargo-deny` blocking, rustfmt and clippy report only (981 rustfmt diffs today; the
  reformat waits for the split). Actions pinned to commit SHAs, read-only permissions, `--locked`.
- **Dependencies.** The RustSec advisory database, cloned and matched against `Cargo.lock` by
  version range, found three real advisories: tokio 1.52.2 (RUSTSEC-2026-0386, AsyncFd, unused
  here), anyhow 1.0.102 (downcast_mut) and event-listener 5.4.1. Updated to tokio 1.54.1 (also
  past 1.54.0's own Interval race), anyhow 1.0.104, event-listener 5.4.2. Accepted in
  `deny.toml` with reasons: bincode unmaintained (the wire format) and rsa (lockfile only, via
  sqlx's MySQL driver, never compiled).
- **The decoder**: a 16 KiB limit (a forged length prefix can no longer reserve memory the
  bytes never back) and a decode warning throttled to one line a second. Trailing bytes stay
  ignored: refusing them, the first cut, broke the protocol's append-a-field compatibility
  (the review caught it).
- **Startup and secrets**: `.env` loads in a plain synchronous `main` before the tokio
  runtime (the `set_var` SAFETY comment is now true); the netcode key is a `NetcodeKey`
  newtype whose `Debug` redacts it; `#![forbid(unsafe_code)]` on protocol, shared and the
  server library.
- **Property tests** (proptest, dev-dependency only): coin arithmetic never creates or
  destroys value, purses up to a trillion platinum; no sequence of moves across base slots,
  full pouches and the cursor changes any item's count (a planted merge dupe is caught at
  once); random and mutated bytes never panic the decoder.
- **`tools/check_all.ps1`** runs every `tools/check_*.gd` through Godot's console build (the

**Fall damage on the server, designed** (`docs/design/server_fall_damage.md`, Phase 4 item 1).
The finding that changes the plan: online, a fall goes through `Combat.receive_player_damage`,
which sends `DamageSelf`, a dev command. An ordinary player's falls have therefore never hurt
them online (the client prints "You hit the ground hard" and the server ignores it); a GM's
falls apply and each writes a `gm_actions` row. `DeathBroadcast`, kept "for client-side fall
damage", has no honest online sender except the Test Panel's Trigger Death button, so B1 can be
closed now by gating it as a dev command, with no client change, instead of after the height
model. References read in source: EQEmu's `Handle_OP_EnvDamage` (the client reports the damage,
the server applies modifiers and never checks the height) and TrinityCore's
`Player::HandleFall` (the server computes a share of max health from the drop, from heights the
client reports). Ours can own both formula and inputs, since our client sends only a direction.
Slice 1 simulates the fall per tick from the height model's ground sampler; an airborne logout
lingers until it lands; a port resolves a fall in progress before moving. Five decisions in §7,
the first being whether to close B1 now.
