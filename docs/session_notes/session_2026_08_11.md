# Session 2026-08-11 — PHASE 2 COMPLETE: the game is hosted, and someone else has played it

Covers a multi-day arc, 2026-08-05 to 2026-08-11, written up on the day Phase 2 closed. Unusual
for this project in that most of it was **not** writing game code: it was building a physical
server from bare metal, deploying to it, hardening it, and getting a second human onto it.

## The machine had to be built first (unplanned)

The R720 arrived unable to boot: `No boot device available` plus a `Boot Failed: Windows Boot
Manager` line. Not a fault. The PERC H710P had **no virtual disk**, so the BIOS had nothing
bootable to find, and the Windows Boot Manager entry was a stale UEFI NVRAM pointer from the
previous owner. Normal state of a wiped, resold PowerEdge.

Built out: VD0 as 4x300GB RAID 10 with a global hot spare (OS + `world.db`), VD1 as 3x1.2TB
RAID 5 mounted at `/data` (backups), Ubuntu Server 26.04 LTS, key-only SSH, UFW default-deny,
unattended security upgrades with automatic reboot explicitly disabled.

Full build record with every gotcha: `docs/deployment/r720_host_setup.md`.

### Worth remembering from the build

- **RAID 10 needs spans declared by hand** on this firmware. Ticking four disks and choosing
  RAID 10 is rejected with a message about spans; you must declare 2 spans of 2.
- **Ubuntu's guided LVM install strands most of the disk.** The default proposed a 100GB root
  on a 554.695GB volume group, leaving 454.695GB unallocated. The fix is to edit the root LV to
  the full size before confirming. The tell afterwards is that the VG vanishes from AVAILABLE
  DEVICES because it has no free extents left.
- **`ProtectHome=true` in the shipped systemd unit** makes `/home` invisible to the service, so
  the initial `~/server` install location was unworkable and had to move to `/opt/projectdawn`
  under a dedicated system account. That is the better practice anyway.
- **A typo in a config variable's NAME looks identical to a missing config file.**
  `PROJECTDAWN_NETCLODE_KEY` produced `PROJECTDAWN_NETCODE_KEY is required`, which is accurate
  and points you at the value rather than the spelling. `sudo cut -c1-32 .env` prints every
  variable name without exposing the secret, which is what made the extra `L` visible.
- **`Restart=on-failure` turns a bad config into a crash loop** that fills the journal faster
  than it can be read. `systemctl stop` first, then diagnose.

## The stale-branch catch (the most important thing that happened)

**The deployed binary was six weeks old and had none of the Phase 1 exploit gates in it.**

`git clone` takes the repo's **default branch**. That was `main` at `98728ea` (26 June). Active
work was on `fix/xp-leveling-overflow`, **30 commits ahead**. The deployed server was therefore
missing `/give` gating (`a765573`), the per-account `is_gm` keystone (`82f55a9`), the Respawn
dead-check (`0d908d1`), attack-while-seated (`3bb9b6d`), the CastSpell class/level gate
(`a96826d`), the `Attack` weapon_path gate (`9089b4b`), the melee swing-rate limit (`335b5b1`),
the login rate-limiter (`a75d9d0` + three follow-ups), and server-authoritative procs
(`b0bdbdd`).

**The only symptom was a missing field in one log line.** The `starting projectdawn-server` line
should carry `dev_cmds=`, which arrived in `a765573`. Its absence dated the build. Nothing else
looked wrong: the server started, listened, loaded corpses and accepted connections.

**Two standing lessons, both now in CLAUDE.md:**
1. A deploy host must track the branch work actually happens on. The default branch is not
   necessarily the live one.
2. `dev_cmds=` present and reading `false` on the boot line is a two-in-one check: the build is
   at least as new as that commit, **and** dev commands are off. Verify after every deploy.

Also surfaced: both repos were far ahead of GitHub (server 30, client 59). Both pushed. Months
of work had been sitting on one machine.

## `server/docs/deployment_linux.md` already existed

Discovered mid-deploy, inside the unpushed server commits: a 213-line deployment guide dated
2026-08-05, "written from source, every gotcha verified, not assumed", plus
`scripts/projectdawn.service` and `scripts/backup.sh`.

It is better informed than the runbook being written alongside it, and it contained at least one
thing that would have cost real debugging time:

> **Clock: verify NTP is running.** ConnectTokens live 30 s and the *client* validates them
> against its own clock. A box more than ~30 s off makes login succeed and then the world
> handshake fail.

Resolved by scoping the two documents rather than merging them. `r720_host_setup.md` owns bare
metal through hardening (which `deployment_linux.md` assumes is already done);
`deployment_linux.md` is authoritative from application deployment onward. Recorded at the top
of the runbook.

## Client fixes found by reading the console (client `a4d67ea`)

Running the exported build from a terminal surfaced two real bugs behind a wall of errors.

**1. `global_position` set before `add_child`** in `remote_player_manager`,
`remote_enemy_manager` and `remote_pet_manager`. Setting `global_position` on a Node3D outside
the tree calls `get_global_transform()` internally, which logs
`Condition "!is_inside_tree()" is true` and returns identity, so the position does not take.
Symptom: an entity can sit at the world origin until the next position broadcast corrects it.
`remote_corpse_manager` and `remote_loot_bag_manager` already had the correct ordering, so the
fix was making three files match two.

**2. Two missing `has_signal()` guards** in `hud.gd::_on_target_changed`. The cleanup block
guards `cast_started`, `cast_ended`, `buffs_changed` and `died`, but not `mp_changed` or
`stamina_changed`. Those two are declared only on `RemotePlayer`; `RemoteEnemy` has just
`hp_changed`, `target_changed` and `died`. So switching away from an enemy target called
`is_connected("mp_changed", ...)` on an object with no such signal and logged
`Nonexistent signal` every time, in pairs.

Both verified gone by playing rather than by reasoning: three kills, three loot bags, three
sequential targets, console silent.

**Left deliberately unfixed** and recorded in the To-Do: `hud.gd:821` and `:823` in
`_show_self_target()` have the same unguarded shape for `hp_changed` and `died`. Those are safe
while `_tracked_target` is restricted to the three remote entity classes, but `corpse_body.gd`
declares no signals at all. Needs confirmation of what can reach that variable before adding
speculative guards.

**Also:** the in-game Report a Bug button pointed at an expired Discord invite
(`options_screen.gd::BUG_REPORT_URL`). Replaced, and the new invite set to never expire.
Fixed in the code, not just the README, which is where it would have been missed.

## Durability

- Nightly `sqlite3 .backup` at 04:00 via `/etc/cron.d/projectdawn-backup`, writing to `/data`
  (VD1), a **different physical array** from the live database on VD0.
- Weekly Windows scheduled task pulling those into Google Drive, which puts one copy outside the
  building. Two problems (automate it, get it off-site) solved by one job, because copying into
  a cloud-synced folder makes the sync do the off-site half.
- **Verified rather than assumed**, twice over: a backup was restored and read (`Pockets|2` came
  back out of the file), and cron's invocation was proven by temporarily setting the schedule to
  every minute and watching new files appear. Running a script by hand proves the script, not
  cron's environment.
- `-m 0` on `mkfs.ext4` for `/data`: ext4's default 5% root reservation would have stranded
  ~110GB on a 2.2TB volume for no benefit on a pure data volume.

## Findings from the first tester session

Both now open items.

**1. Respawn death-loop (high).** She died, respawned on the spot at partial HP beside the two
mobs that had just killed her, was taking damage 5 seconds later, and was dead again 20 seconds
after that. Two corpses, twenty seconds apart. This is the existing *"Respawn at bind"* item,
recorded 2026-07-20 from a solo playtest as a UX gap wanting a redesign pass. In the hands of a
new player it is an **unwinnable loop**. Escalated in the To-Do. Even a few seconds of
post-respawn invulnerability would break it without needing the full bind system.

**2. Login rate limit forced a duplicate account (medium).** She logged out, tried to log back
in, tripped the 5-per-60s cap, and **created a second account rather than waiting**. She now has
two accounts and two characters, and there is no account-deletion tooling to tidy that up. The
Phase 1 gate worked exactly as designed; the threshold is wrong for a real human on their first
evening. The threat model has also moved: nothing reaches 8765 without being on the tailnet, so
brute-force risk is currently near zero while the usability cost is demonstrated. Decision
pending.

Worth noting the shape of both: **neither was findable without a second person.** One is a
design gap that only bites someone with no gear and no map knowledge; the other is a security
control that only misfires against someone typing a password for the first time.
