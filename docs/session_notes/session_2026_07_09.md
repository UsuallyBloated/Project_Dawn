completed set was invisible (a redo attempt silently paid nothing), and the phase-1 review's

zero gameplay, bounded only by `level_req`). Slice A moves objective state to the server; the
client becomes a renderer. Design fork resolved by the user this session: **NPC turn-in
(classic EQ)** — killing the last mob marks the quest "Ready", the reward pays at the giver.

## Adversarial review + fixes folded in

Ran a 4-dimension finder workflow (exploits / server / client / wire-lockstep) with a
3-refuter verification stage. The verify stage was interrupted by a session limit, so I
adjudicated the 10 finder findings directly (I wrote the code). Two real clusters fixed;
the rest are by-design or dev-only and noted:

**Fixed — rollback desync (review findings 3/7/10).** The client had decided whether to undo
an optimistic accept by string-matching the rejection reason against a hardcoded list. That
was fragile both ways: an accept that DB-failed sent a reason NOT in the list (phantom active
quest), and a turn-in "already completed" reason WAS in the list (erased a still-tracked
entry). Fix: `ServerWorldMsg::QuestRejected` gained a `rollback: bool` the server sets itself
(true only for accept-phase refusals). Client obeys it; `ACCEPT_REJECT_REASONS` deleted. (Wire
edit in place — PD_W0024 was uncommitted.)

**Fixed — accept/abandon persistence + ordering (findings 4/5/6/9).** Accept and abandon each
did an awaited SQLite write inside the tick, and same-tick abandon+accept was processed out of
arrival order (bucketed per message type) → a forged client could thrash writes and self-
desync. Fix: accept/abandon now share ONE arrival-order queue (`quest_lifecycle_intents`);
their drains only mutate in-memory `active_quests` + mark `quests_dirty`; the once-per-tick
flush (step 6-ter) and the reap flush now RECONCILE (upsert if still active, else delete the
row). Writes are bounded to one-per-quest-per-tick regardless of message volume, and the final
in-memory state (order-correct) is what persists. Turn-in keeps its explicit
persist-completion-then-delete (once-per-quest-ever, not a spam vector).

**Noted, not fixed (by design or dev-only):**
- test_q1 + wolf_threat both target "Wolf" so one set of 5 kills advances both — shared kill
  counting across held quests is authentic EQ, and holding test_q1 needs the dev-only Test
  Panel. Dev-content overlap, not a live exploit.
- A forged AcceptQuest can skip the dialogue quest-chain (e.g. take rotfang before wolf) — the
  chain is soft UX gating; `level_req` is the hard gate and IS enforced, and the objective
  check still forces the gameplay, so nothing is gained.
- NPC turn-in dialogue rows are unreachable in local/Test-Room mode (the local path auto-
  completes and never sets READY) — the reward still lands there; local mode is vestigial.

## Playtest 2026-07-10 (two-client, both server logs preserved)

Ran the slice-A checklist across two server runs (`quest_phase2_sliceA_serverlog_run1.log`
preserved next to the checklist; run 2 is the post-restart run). **The quest system passed
every path** — both logs confirm: accept, server-side kill counting, group split (630/630 for
2 members), turn-in gating (test_q1 rejected "objectives incomplete" at progress [0], then
completed after the kills), level-gate rejection (rotfang below level_req at level 3), abandon
+ re-accept + complete (char 104), pay-once, and — the phase-2 headline — **objective progress
survived a real server restart** (char 103's wolf_threat carried run1→run2 and turned in). The
one de-level in run 1 (char 102: 7→6) is the death penalty, not a quest issue.

Four follow-ups the tester flagged; three fixed this session, one diagnosed as out-of-scope:

- **Fixed — completed quest showed "0 / 5".** A quest rebuilt from `QuestSnapshot` after relog
  marked objectives done but left the count at 0 (the snapshot carries no per-objective counts
  for finished quests). New `_mark_objectives_satisfied` pins count to the requirement; used in
  both the snapshot rebuild and `on_server_completed`.
- **Fixed — re-completing a done quest was silent.** The Test Panel "Complete Test Quest"
  re-click hit `complete_quest`'s already-COMPLETED early-return with no feedback. It now logs
  "You have already completed …" (covers both the in-journal and completed-id-only cases).
- **Fixed — quest XP read "party experience".** Server-driven quest XP arrives via
  `apply_remote_xp`, which had no source tag, so it fell through to the group/kill wording. The
  server now sends `QuestCompleted` just BEFORE the reward `XpGained` (same reliable-ordered
  channel); `on_server_completed` sets a one-shot `PlayerStats.note_next_xp_source("quest")`
  the next `apply_remote_xp` consumes, and the combat-log line now reads "You gained N quest
  experience!".
- **Diagnosed, NOT a quest regression — bank item deposit doesn't show in the Items tab.** The
  server correctly removes the item, deposits it into the persisted vault, and fans a fresh
  `BankItemSnapshot` (`tick.rs` ~6164-6184; log shows `deposited=1`), so the item is SAFE and
  reappears on relog. The wire is append-only and this slice touched zero bank code, so this is
  a pre-existing client-side BankWindow Items-tab live-refresh bug (the banker slice-2 checklist
  was already mid-playtest). Tracked for a separate pass.
