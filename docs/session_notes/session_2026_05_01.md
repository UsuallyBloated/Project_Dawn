## Multiple enemy types — Caster & Healer

### `scripts/enemy.gd` — new exports

**Caster group:**
- `spell_damage: int` — 0 = melee only; > 0 = ranged spell caster
- `spell_interval: float` — seconds between spell casts (default 3.0)
- `caster_range: float` — preferred engagement distance (default 8.0)
- `flee_range: float` — backs away if player enters this distance while kiting (default 3.0)
- `spell_damage_type: SpellData.DamageType`

**Healer group:**
- `healer_flee_hp: float` — fraction 0–1; flee + self-heal when HP drops below this (0 = disabled)
- `heal_amount: float` — HP healed per tick while fleeing
- `heal_interval: float` — seconds between self-heals (default 5.0)

### New state and helpers

- `State.FLEE` added to the enum; included in `_physics_process` match
- `_spell_cooldown`, `_heal_cooldown` vars added alongside `_attack_cooldown`
- `_should_flee() -> bool` — `healer_flee_hp > 0.0 and hp / max_hp < healer_flee_hp`
- `_tick_attack_caster(delta, dist)` — faces player; backs away if player is within `flee_range`; transitions back to CHASE if player is > `caster_range × 1.3`; respects silence; fires `_do_cast_spell()` on interval
- `_tick_flee(delta)` — moves toward spawn; periodically calls `_do_cast_spell()` and self-heals; transitions back to CHASE when HP recovers above threshold
- `_do_cast_spell()` — deals spell damage via `Combat.receive_player_damage()`; has a 5% crit multiplier; spawns incoming number and impact light

### State machine changes

- `_tick_chase()`: checks `_should_flee()` first; uses `caster_range` as engage distance when `spell_damage > 0` (instead of `melee_range`)
- `_tick_attack()`: checks `_should_flee()` first; branches on `spell_damage > 0` to `_tick_attack_caster()`

### `scripts/enemy_spawner.gd` — new override groups
- **Caster Overrides**: `spell_damage_override`, `spell_interval_override`, `caster_range_override`, `spell_damage_type_override`
- **Healer Overrides**: `healer_flee_hp_override`, `heal_amount_override`, `heal_interval_override`
- All applied in `_apply_overrides()`; zero/falsy values skip the override (inherit from scene)

- Introduces a new autoload or base class

## Vendor NPCs — Bug Fixes

The vendor system (`vendor_window.gd`, `VendorManager`, `VendorDefinitions`) was already fully built and wired into the HUD. Two bugs were discovered and fixed this session.

### Bug 1: `_append_stat_lines()` missing — `scripts/vendor_window.gd`

`_refresh_detail()` called `_append_stat_lines(item, stats_lines)` at line 264 but the function was never defined. Any item click would crash at runtime.

**Fix:** Implemented `_append_stat_lines(item: ItemData, lines: Array)` in the Helpers section. Shows:
- Weapons: damage range, delay, weapon skill, proc info (chance % + damage)
- Armor: armor bonus
- Stat bonuses: STR/AGI/DEX/INT/WIS/CON/HP/MP (only non-zero)
- Consumables: HP or MP regen rate/duration, heal-on-use, mana-on-use

### Bug 2: XP signal bypassed on death — `autoloads/player_stats.gd` + `autoloads/player_death.gd`

`player_death._die()` used `PlayerStats.xp = max(0, PlayerStats.xp - xp_loss)` — a direct property assignment that bypasses the `xp_changed` signal. The XP bar on the HUD would not update when XP was lost on death.

**Fix:** Added `lose_xp(amount: int)` to `player_stats.gd` (parallel to `add_coins`/`spend_coins`):
```gdscript
func lose_xp(amount: int) -> void:
    xp = max(0, xp - amount)
    xp_changed.emit(xp, xp_to_next)
```
`player_death._die()` updated to call `PlayerStats.lose_xp(xp_loss)` instead of direct assignment.

### Cleanup: `_append_stat_lines` consolidated to base class

`_append_stat_lines(item, lines)` was already defined in `scripts/draggable_panel.gd` (the base class). The duplicate added to `vendor_window.gd` was removed. The base class version was extended to also include weapon damage/delay/skill, `bonus_armor`, and proc info — all `DraggablePanel` subclasses (vendor window, inventory tooltips, etc.) inherit the full implementation automatically.

## Code Review Pass — Bug Fixes

Full audit of all code written this session. Two bugs found and corrected.

### Bug 1: `@onready` null access — `scripts/enemy_spawner.gd`

**Root cause:** `_apply_overrides(enemy)` was called at line 81 of `_spawn()`, _before_ `add_child(enemy)` at line 87. `apply_named()` was called at the end of `_apply_overrides()`. Inside `apply_named()`, `_name_label` (`@onready var`) is null until `_ready()` runs, which only happens after the node enters the scene tree via `add_child()`. Any named mob spawn would crash at runtime.

**Additionally:** `_ready()` sets `hp = max_hp`. If `apply_named()` ran before `_ready()`, `hp` would later be reset to the un-multiplied `max_hp` value — making HP scaling silently incorrect even if the null crash were somehow avoided.

**Fix:** Removed `apply_named()` from `_apply_overrides()`. Added a guarded call in `_spawn()` immediately after `add_child()`:
```gdscript
get_tree().current_scene.add_child(enemy)
enemy.global_position = global_position + offset
if named_mob_id != "":
    enemy.apply_named(named_mob_id)   # @onready vars now safe; _ready() has run
```

**Note:** The session notes entry under "Named / Boss Mobs" incorrectly stated `_apply_overrides()` calls `apply_named()`. The correct call site is `_spawn()`, after `add_child()`.

### Bug 2: Cross-system coupling in `autoloads/quest_manager.gd`

**Root cause:** `notify_collect()` used `Crafting.count_item(item_name) if Crafting.has_method("count_item") else 0` to determine how many of an item the player had. This is wrong in two ways: (1) inventory counts belong to `Inventory`, not `Crafting`; (2) the `.has_method()` guard is a sign the call was never stable to begin with.

**Fix:** Replaced with direct increment — same pattern `notify_kill()` uses. Each call to `notify_collect(item_name)` increments `count_done` by 1, capped at `count_needed`:
```gdscript
obj["count_done"] = mini(obj["count_done"] + 1, obj["count_needed"])
```
No external system queries. The caller is responsible for calling `notify_collect()` once per item actually picked up.

## Loot System Bug Fix

### Root cause: `ResourceLoader.exists()` returns false for valid `.tres` files in Godot 4.3

Every item-loading call site used a guard:
```gdscript
if ResourceLoader.exists(path): return load(path) as ItemData
```
In Godot 4.3, `ResourceLoader.exists()` intermittently returns `false` for valid `.tres` resource files, causing the guard to silently skip the load. The result: all named mob loot tables returned empty, vendor stock wouldn't load, crafting ingredients couldn't be found, mining nodes produced nothing.

**Fix:** Removed the `ResourceLoader.exists()` guard from all call sites. `load(path) as ItemData` already returns `null` for missing/invalid files — no separate guard needed.

## Inventory System Redesign

Complete rewrite of the inventory model. Old system gated all items behind bag slots (items could only exist inside a bag). New system has 8 base slots where both items and bags live directly; bags expand the inventory by opening additional slots when clicked.

### `autoloads/inventory.gd` — full rewrite

**Old model:** `NUM_BAG_SLOTS = 6` dedicated bag slots; items could only go inside bags; `equip_bag()` / `unequip_bag()` moved bags in/out.

**New model:**
```gdscript
const BASE_SLOT_COUNT := 8
var base_slots: Array = []   # null | {"item": ItemData, "count": int}
var bag_contents: Array = [] # parallel: null | Array[bag_num_slots]
```
- 8 base slots accept any item type including bags
- A bag at `base_slots[i]` expands via `bag_contents[i]` (no bag-in-bag)
- Stacking uses `item_name` comparison (not reference equality) so items from different loot events stack correctly
- `stack_all()` uses `item_name` as dictionary key for the same reason

New API: `get_base_slot(i)`, `set_base_slot(i, val)`, `clear_base_slot(i)`, `remove_base_at(i)`
Removed: `equip_bag()`, `unequip_bag()`, `bag_slot_changed` signal, `NUM_BAG_SLOTS`

### `scripts/inventory_window.gd` — full rewrite
- Now shows a 2×4 grid (`COLS=2`, `SLOT_SIZE=48`) of 8 base slots
- Bags show a slot-count badge; clicking a bag slot toggles its `BagWindow`

## Target-of-Target Frame — Position & Sizing Fix

`scripts/hud.gd` `_build_tot_frame()`

**Problem:** Using `set_anchor_and_offset(SIDE_LEFT/RIGHT, 1.0, offset)` on a dynamically-created `Control` added to a `CanvasLayer` caused the panel to span the full screen width. The anchor=1.0 calculation needs a valid parent rect, which isn't available when called before `add_child()`.

**Fix:** Switched to the same pattern used by all other `DraggablePanel` windows — `add_child()` first, then `setup(pos, size)` with absolute coordinates computed from `get_viewport().get_visible_rect().size`.

```gdscript
add_child(_tot_frame)
var vp := get_viewport().get_visible_rect().size
_tot_frame.setup(Vector2(vp.x - 154.0, 4.0), Vector2(150.0, 34.0), Vector2(100.0, 28.0))
```

Result: 150×34px panel pinned to the top-right corner, 4px margin from screen edge.
