# Session — 2026-05-11 / 2026-05-12

**Track 4 — Player state replication.** Five sub-tasks bringing
combat-adjacent visibility online between players: HP/MP/stamina bars,
cast bars, buff lists, hit/miss/evade floating text, and
death/respawn. Plan source: [handoff_track_4.md](handoff_track_4.md).
Order followed verbatim 1 → 5 per the handoff. Two adjacent
follow-ups bundled in: the EnterWorld lobby gate (E) and the test-panel
damage button + launcher-mode mount (F). Spans two days because the
user broke between sub-task 2 and sub-task 3.

Trust model carried forward per the handoff: combat math stays
client-local in Track 4. The owning client computes outcomes (its own
HP, crits, miss rolls); the server is a fan-out relay. Server-
authoritative combat is Track 6+; server-authoritative enemies are
Track 5. PvP HP application is deferred — Track 4 broadcasts only
the *visual* events.

## Open questions

Answered before the first commit per the handoff:

1. **Spell id strategy.** Option (b): `ServerWorldMsg::CastStart` /
   `::CastComplete` carry `spell_name: String` instead of
   `spell_id: u32`. No stable spell-id table on either side; the
   reliable channel makes the string cost negligible.
2. **Buff replication shape.** Snapshot. Whole list on every
   `BuffManager.buffs_changed`. ~300 B per change is trivial and the
   payload can't desync if a message drops.
3. **Death scene.** Option (a): `DeathBroadcast` → `EntityDied`;
   respawn lands silently via the next `ResourceUpdate` (peer HP
   coming back > 0 stands the body up). No separate Respawn variant.
4. **Resource broadcast throttle.** 5% of max **OR** 250 ms minimum
   gap. Tunable constants at the top of the broadcaster autoload.
5. **Own-id hit filter.** Filter `target == own_id` and route through
   the incoming-text path (different render from outgoing).
6. **XP / LevelUp.** Deferred. Group XP sharing still rides the
   legacy enet path; migrating that is a separate track alongside
   server-authoritative enemies.
7. **Server live during the session.** User confirmed, ran with
   `cargo run -p projectdawn-server --release 2>&1 | Tee-Object
   server.log` throughout.

WORLD_PROTOCOL_ID bumped **once** for the whole Track 4 batch:
`PD_W0002 → PD_W0003`. Every sub-task appends its variants under
this id; future tracks bump again only when they break the wire.

## Sub-task 1 — Resource bar replication (HP / MP / stamina)

The wire foundation the other sub-tasks copy. Owning client broadcasts
its resources on every change (throttled), server fans out three
`HealthUpdate` / `ManaUpdate` / `StaminaUpdate` variants to in_world
peers, peer's HUD target frame renders them when targeting.

**Protocol.** `ClientWorldMsg::ResourceUpdate { hp, max_hp, mp,
max_mp, stamina, max_stamina }` appended. `ServerWorldMsg::ConnectOk`
extended to also carry `name / race / class / level` (more on that
below — bundled with sub-task 1 because launcher-mode characters
otherwise land in world.tscn with no class set).

**Server.** `PerConnection.last_hp / last_max_hp / ... /
resource_state_set` cache fields. `Outcome::ResourceFanOut` returned
from the handler arm. Tick loop collects senders into
`resource_fanouts: Vec<ClientId>` with per-sender dedup so a burst
in one tick coalesces to one fan-out. New step 4b fans out to every
other in_world peer using `fan_out_resources` (encode each
`HealthUpdate`/`ManaUpdate`/`StaminaUpdate` once, clone bytes per
recipient — same pattern as Track 3's Position fan-out). Step 4a
extended to seed each in_world peer's cached resources to a
JustEnteredWorld newcomer.

**Lobby class-init fix.** Launcher-mode discovery: `lobby._on_app_connected`
never called `PlayerStats.apply_character`, so the character entered
world.tscn classless with default 100/100/100 stats. Server knows
race/class/level from the DB-loaded `CharacterSpawn` but
`EntitySpawn` fan-out skips self by design (`ConnectOk` was supposed
to be the own-spawn signal). Extended `ConnectOk` to carry
name/race/class/level; lobby reads them via new `Net.get_own_*`
getters and calls `apply_character` before flipping the Enter World
button. CharacterSetup's existing `character_applied` cascade then
initializes Skills, Spells, WeaponSkills, ArmorSkills,
CastingSkills, Languages.

**gdext-net.** `send_resource_update` func on `NetClient`. Three new
typed signals (`health_update`, `mana_update`, `stamina_update`).
`connect_ok` signal extended with the new identity fields. Existing
`world_smoke.rs` destructuring updated to `{ player_id, .. }` so the
new fields don't break the older test.

**Client.** New autoload `NetCombatBroadcaster` hooks PlayerStats's
hp/mp/stamina/stats_changed signals. Throttle: broadcast on any
single resource moving >5% of its max OR after 250 ms of pent-up
small changes. No traffic when nothing moves. The apply_character
cascade in lobby fires the first broadcast naturally — no force-on-
connect (forcing earlier would send pre-apply default stats).

**Render — pivoted mid-sub-task.** Initial implementation put three
overhead bars above the peer's capsule. User feedback during manual
verification redirected to the target-frame approach (matches the
game's pattern: target a peer like an enemy, target frame shows
their state). Wire infrastructure kept; only the render moved.

Concretely:
- Stripped HpBar/MpBar/StBar nodes + the bar shader from
  `remote_player.tscn`. Reverted to capsule + NameLabel.
- Added `mob_name`/`is_dead`/`set_targeted` accessors to RemotePlayer
  and joined the `remote_players` group in `_ready` so the existing
  Targeting + Combat plumbing accepts it.
- `Targeting._click_target` accepts the new group (same branch as
  enemies / NPCs). `Combat.set_target` falls into the non-enemy
  else branch — auto-attack stays off, which is correct: PvP combat
  lands in Track 6.
- `TargetFrame/VBox` gained `MPBar` + `StaminaBar`, both
  `visible=false` by default. HUD's `_on_target_changed` routes
  remote_players through new `_setup_peer_target`; subscribes to the
  peer's `hp_changed`/`mp_changed`/`stamina_changed` signals so bars
  tick with each broadcast.
- Level label cleared on peer targets per user feedback (peer level
  not surfaced in the target frame).

**Verification.** `cargo test --release` 8/8 (added
`two_clients_resource_fanout`). Manual two-instance: peer's target
frame shows HP/MP/Stamina, bars update within ~250 ms of a damage
event on the other client.

## Follow-up E — EnterWorld gate on spawn fan-out

User noted during sub-task 1 verification: A could see B's static
capsule while B was still at the "Enter World" screen. Server fans
out `EntitySpawn(B)` to A the moment B's app-Connect handshake
completes — which is when the lobby button appears, NOT when B
actually leaves the lobby.

**Fix.** New `ClientWorldMsg::EnterWorld` variant; sent by lobby's
`_on_enter_world_pressed` before the scene change. Server tracks
`conn.in_world` separately from `conn.ready`. The fan-out trigger
moves from "JustConnected" (renamed to `JustEnteredWorld`) to the
EnterWorld arrival. EntityDespawn-on-disconnect also gates on
`in_world` (no point despawning a client peers never knew about).
Position fan-out (step 6) and resource fan-out (step 4b) gate on
in_world both ways — lobby-state clients no longer waste bandwidth.
ConnectOk still fires on the original handshake so the lobby's
identity-init flow stays intact.

Test infrastructure updated: each `WorldClient` in
`world_two_clients.rs` and `world_smoke.rs` sends EnterWorld
immediately after ConnectOk and pumps its transport for ~200 ms so
the bytes actually leave the outgoing buffer before `start()`
returns.

Commits: server `2dd47bc`, launcher `8bfb64b` (sub-task 1 mirror
amended), Project_Dawn `667c9f7`.

## Follow-up F — Test-panel damage button + launcher-mode mount

The handoff suggested a "Take 20 dmg" button on the existing test
panel to verify resource replication without needing a mob in range.
Implemented in the COMBAT FLAGS section: routes through
`Combat.receive_player_damage(20, null, "Test Panel")` so the full
damage path fires (evasion, absorbs, armor reduction, broadcaster
fan-out).

Also discovered: the test panel only mounted when
`Network.is_test_room` was true (the legacy local-test flow). In
launcher mode it was unreachable. Extended the gate in `world.gd`
and `dungeon_world.gd` to also mount when `Net.is_launcher_mode()`.
Strip-this-when-shipping comment included.

Bundled in the same commits as follow-up E.

Also bundled in: a defensive cleanup in `remote_player_manager.gd`
after a transient duplicate-RemotePlayer artifact surfaced during
the first EnterWorld test. Root cause was a race in the
scene-change detection: `_by_id.clear()` dropped references without
freeing the underlying nodes, relying on the scene change itself to
free the children. A transient `current_scene` null during
`change_scene_to_file` could trip `scene != _last_scene` without
actually swapping, leaving live nodes orphaned. Two belt-and-
suspenders fixes:

1. The scene-change branch now `queue_free`s every node in
   `_by_id.values()` before clearing the dict.
2. `_on_entity_spawn` scans the live scene for any `RemotePlayer`
   with matching `char_id` that isn't tracked and frees the orphan
   before instantiating the new one.

Neither path should fire in normal flow, but together they guarantee
at most one live RemotePlayer per char_id regardless of scene-change
timing.

## Sub-task 2 — Cast bar replication (option 2b)

User picked **2b** (cast bar in target frame, like the resource bars)
over **2a** (overhead bar). Awareness-vs-inspection tradeoff in
favor of consistency with the no-overhead-clutter rule.

**Protocol.** Three new `ClientWorldMsg` broadcast variants:
`CastStartBroadcast { spell_name, duration }`,
`CastCompleteBroadcast { spell_name }`,
`CastFailBroadcast { reason }`. Existing `ServerWorldMsg::CastStart`
/ `CastComplete` switched from `spell_id: u32` to
`spell_name: String` per Q1; `CastFail` gained `caster: EntityId`
for symmetric fan-out shape.

**Server.** Three new Outcome variants carrying the payload. Handler
arms validate `conn.ready`, update `PerConnection.cast_spell_name /
cast_total_duration / cast_set_at` cache, return the matching
outcome. Cache cleared on Complete/Fail. New step 4c drains the
combat events into `fan_out_cast_start` / `_complete` / `_fail`
helpers. Step 4a extended: seed new in_world joiners with each
mid-cast peer's remaining duration (`total - elapsed`, clamped to
> 0; if elapsed exceeds total the cast was abandoned without a Fail
and we skip the seed entirely).

**Client.** NetCombatBroadcaster hooks `Spells.casting_started` →
broadcast Start (with `spell.cast_time`); `Spells.spell_cast` →
Complete *only if cast_time > 0* (spell_cast fires for instant
casts too); `Spells.casting_cancelled` → Fail("interrupted") if a
start was previously sent. `_last_cast_spell_name` tracks state.

**RemotePlayer.** `cast_started`/`cast_ended` signals,
`cast_spell_name`/`cast_duration`/`cast_start_time` vars,
`is_casting()` + `cast_progress_ratio()` helpers reading
`Time.get_unix_time_from_system()`. `_process` polls a
duration-elapsed timeout (defensive — if the casting peer crashed
before Complete/Fail, the bar would linger; 0.5 s grace).

**HUD.** TargetFrame gained `CastBar` (ProgressBar, gold/XP color)
and `CastLabel` (spell name), both hidden by default. HUD's
`_setup_peer_target` connects to the peer's cast signals; if the
peer `is_casting()` at target-time the bar shows immediately.
`_process` ticks `target_cast_bar.value` from
`cast_progress_ratio()` so the bar fills between server messages
(server sends Start + duration once; client interpolates progress
locally).

`cargo test --release` 9/9 (added `two_clients_cast_fanout`).

Commits: server `292a982`, launcher `41c672e`, Project_Dawn `9b87f6c`.

## Sub-task 3 — Buff snapshot replication

Snapshot model per Q2. Whole buff list re-broadcast on every
`BuffManager.buffs_changed`.

**Protocol.** `ClientWorldMsg::BuffSnapshotBroadcast { buffs:
Vec<(String, f32)> }` and a new `ServerWorldMsg::BuffSnapshot {
target, buffs }` variant. The pre-existing
`BuffApplied`/`BuffRemoved`/`HotTick`/`DotTick` variants stay
defined for future delta replication but remain unused in Track 4.

**Server.** `PerConnection.buff_snapshot: Vec<(String, f32)>` +
`buff_snapshot_set` flag. `fan_out_buff_snapshot` helper. New
`Outcome::BuffSnapshotFanOut` deduped per-sender like resources.
New step 4d fans out to in_world peers excluding sender. Step 4a
seeds new joiners with each peer's cached snapshot (sends an empty
list if the peer has explicitly broadcast "no buffs" — `resource_state_set`-
style flag so a never-broadcast peer doesn't clear the new client's
view).

**gdext-net.** `send_buff_snapshot_broadcast` takes parallel
`PackedStringArray names` + `PackedFloat32Array durations` (cheap
interop; zipped into `Vec<(String, f32)>` Rust-side). Mismatched
lengths silently truncated to the shorter. `buff_snapshot` typed
signal on the receive path with the same parallel-array shape.

**Client.** `BuffManager.get_snapshot_arrays()` walks every buff
source the local buff bar surfaces — HoTs, Absorb, Evade, Food,
Drink, Speed, Haste, MpRegen, Stat, PrimaryStat, DamageShield,
Stealth, Lich — and emits parallel arrays. 0.0 duration means
"indefinite/toggle" (Lich, raw Absorb); receiver displays just the
name. NetCombatBroadcaster hooks `BuffManager.buffs_changed` and
pushes through `Net.broadcast_buff_snapshot`.

**HUD.** TargetFrame gained `BuffsLabel` (wrap-enabled multi-line
Label below CastLabel, hidden by default). Renders as one line per
buff: `"<name>  <duration>s"` or just `<name>` for 0-duration
entries. Empty snapshot hides the label. RemotePlayer caches the
arrays; HUD's `_setup_peer_target` subscribes to the peer's
`buffs_changed` and refreshes the label.

`cargo test --release` 10/10 (added `two_clients_buff_snapshot_fanout`).

Commits: server `a14d5bd`, launcher `4e54d8a`, Project_Dawn `5d08033`.

## Sub-task 4 — Hit / Miss / Evade floating text

Attacker broadcasts the combat outcome; targeted peer's client
renders incoming text near the local player; any other observer
renders outgoing damage text over the targeted RemotePlayer. Combat
math stays client-local — these messages are pure visualization
fan-out; the target's HP isn't driven by them (PvP HP application
is Track 6).

**Protocol.** Three new `ClientWorldMsg` broadcasts:
`HitBroadcast { target, amount, crit, dmg_type }`,
`MissBroadcast { target }`, `EvadeBroadcast { target }`. Existing
`Hit`/`Miss`/`Evade` `ServerWorldMsg` variants reused; `CastFail`
gained `caster: EntityId` while we were in there (symmetric shape).

**Server.** Three new Outcome variants carrying the event payload.
`combat_fanouts: Vec<(ClientId, CombatEvent)>` collected during
dispatch, **not** deduped (Hit/Miss/Evade are one-shot ordered
events). New step 4e drains and fans out to in_world peers excluding
sender. Three helpers: `fan_out_hit/_miss/_evade`.

**gdext-net.** `send_hit_broadcast` / `_miss_broadcast` /
`_evade_broadcast` funcs. `DamageType` passed as `i64` across the
FFI; clamped to known range via `damage_type_from_u8` (out-of-range
falls back to Physical). Three new typed signals (`hit`, `miss`,
`evade`).

**Client.** `Combat.deal_damage_to_target` detects RemotePlayer
target → broadcasts Hit, skips `take_damage` (peer has authority
over its own HP). Enemy-target path unchanged.
RemotePlayerManager's `_on_hit`/`_miss`/`_evade` handlers route to
DamageNumbers: `target == own_player_id` → `spawn_incoming` near
the local player; otherwise → `spawn_damage`/`spawn_miss` over the
targeted RemotePlayer's position. Evade reuses spawn_miss
(DamageNumbers has no distinct evade visual yet).

**Test panel.** Three new buttons in COMBAT FLAGS — "Hit Target
(20)" (red), "Miss Target" (yellow), "Evade Target" (purple). Each
requires a RemotePlayer target (group `remote_players` check);
reports via CombatLog if it no-ops. `_resolve_peer_target` helper
consolidates the gate. Locally spawns the matching DamageNumbers
call alongside the broadcast so the attacker's own client sees text
immediately.

**Diagnostic side-track.** First manual test showed no floating text
on either side despite both broadcast lines being received. Added
debug CombatLog instrumentation in the test panel and
RemotePlayerManager._on_hit; confirmed the chain fired end-to-end.
Plain Label3D bypass (green "DIAG" marker) confirmed rendering
worked. Root cause: `GameSettings.floating_text_enabled` was off in
the user's save (toggled at some prior session via Options →
Interface). Once re-enabled, the system worked as designed.
Diagnostic instrumentation stripped before commit.

`cargo test --release` 11/11 (added `two_clients_hit_fanout`).

Commits: server `9ce395b`, launcher `171099f`, Project_Dawn `dd4216e`.

## Sub-task 5 — Death / respawn replication

Per Q3 option (a): dying client broadcasts `DeathBroadcast`; server
relays `EntityDied { id }` to in_world peers; peers play a fall-over
animation in place. Respawn lands silently via the next
`ResourceUpdate` carrying hp > 0 (no separate Respawn variant by
design).

**Protocol.** `ClientWorldMsg::DeathBroadcast` (no payload — the
dying client's char_id is implicit from the sender). Existing
`ServerWorldMsg::EntityDied { id }` reused for fan-out.

**Server.** `DeathBroadcast` handler clears the cast cache (a corpse
isn't mid-cast), leaves the resource cache intact (the dying
client's `_respawn` will naturally broadcast new resources that
drive the stand-up), returns `Outcome::DeathFanOut`.
`death_fanouts: Vec<ClientId>` with dedup-on-insert (defensive
against a malformed dying client sending Death twice). New step 4f
fans out via `fan_out_entity_died`.

**gdext-net.** `send_death_broadcast` func + `entity_died` typed
signal.

**Client.** `PlayerDeath._die()` calls `Net.broadcast_death()` before
scheduling `_respawn`. The natural `set_hp/set_mp/set_stamina`
cascade inside `_respawn` fires ResourceUpdate broadcasts that drive
the peer's stand-up.

**RemotePlayer.** New `apply_death` tweens `rotation.x` to PI/2 over
0.5 s (falls onto its side) and dims the nameplate. Sets
`is_dead = true`. `apply_health_update` detects "was_dead and
new_hp > 0" → calls `_apply_respawn`: clears the snapshot buffer
and `_last_seq` so the next Position broadcast snaps via the
cold-start branch (no slide-from-death-spot to bind-point), tweens
rotation back to 0, restores nameplate color.
`on_position_update` drops snapshots while `is_dead` so any stray
Position updates from the dying client don't slide the corpse;
`_physics_process` early-returns while dead.

`cargo test --release` 12/12 (added `two_clients_death_fanout`).

Commits: server `9e2fd8d`, launcher `fc17ff1`, Project_Dawn `9088bf9`.

## Pending / deferred / out-of-scope

- **XP / LevelUp replication.** Per Q6 deferred. The group XP
  sharing path still uses Godot's legacy enet MultiplayerAPI, not
  the renet world channel — migrating it is a separate track,
  likely alongside server-authoritative enemies.
- **PvP HP application.** Track 4 broadcasts hits but doesn't apply
  damage to peer HP. The trust model (each client authoritative on
  own HP) makes this safe but means peer attacks today are visual-
  only. Lift in Track 6 when server-authoritative combat lands.
- **Auto-attack on peer targets.** `Combat.set_target` falls into
  the non-enemy else branch for peers (auto-attack timer stays off).
  Targeting a peer is for inspection. PvP flagging design (handoff
  to-do item) is a prerequisite for enabling peer auto-attack.
- **Spell-resist / damage-type mapping for peer spells.** Spells
  don't currently target peers (`has_valid_target` requires the
  `enemies` group), so this never fires. When PvP spells land,
  `SpellData.DamageType` ↔ `NetProtocol.DamageType` mapping needs
  consolidation (the enums don't currently align — SpellData has
  HEALING/NONE, NetProtocol has PHYSICAL/POISON).
- **GameSettings.floating_text_enabled gate.** Surfaced during
  sub-task 4 testing as a non-obvious silent failure — the master
  toggle was off in the user's save. Test-panel buttons could be
  designed to bypass this for diagnostic purposes (force visible
  feedback regardless of user prefs). Out of Track 4 scope.
- **Cast bar duration ticks server-snapshotted, not live.** Sub-
  task 2 ticks the bar via `cast_progress_ratio()` reading
  `Time.get_unix_time_from_system()` — works for the live-cast case
  but new-joiner seeds carry a frozen "remaining" value. Currently
  the seed is also treated as "fresh duration" and ticks down from
  there; mild inaccuracy but visually consistent.
- **Buff durations on the peer's view are snapshot values, not live
  counters.** Each `BuffManager.buffs_changed` fires a fresh
  snapshot, so the displayed time looks like it ticks in steps. If
  it feels janky, a future polish pass can interpolate locally.
- **Evade visual.** Reuses `spawn_miss` (gray "Miss" text) because
  `DamageNumbers` has no distinct evade type yet. Future polish.
- **WORLD_PROTOCOL_ID enforcement** still server-side only — the
  Track 3 finding carries forward unchanged.
- **Test-panel race/class dropdown desync.** The test panel can call
  `PlayerStats.apply_character` to change race/class mid-session.
  In launcher mode this desyncs from the server's authoritative
  class. Documented as a known limitation; a launcher-mode lockout
  on the dropdowns is a small follow-up if it becomes a problem.
- **Resource fan-out throttle tunable.** 5% / 250 ms is the
  handoff's starting point. Tune by ear as combat density
  increases.
