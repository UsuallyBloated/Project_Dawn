Two things to know before the dates

Both came out of reading the repo rather than the to-do list, and both change the plan.

Correction

Two weeks of finished work is sitting in the open column.

The to-do list still shows quest phase 2 as open with six sub-items: the journal wiping on logout, the completed set not syncing, item rewards being test-room-only, kill quests auto-completing, no abandon button, and Brom's dialogue unwired. All six shipped between July 9 and July 15. The session notes say so by name ("closes the last of the plan's 7 root problems") and the commits match.

A documentation clean-up landed on July 16 that was specifically meant to catch stale claims like this, and it caught several real ones: the wire protocol was recorded ten versions behind reality. It walked straight past this entry.

Resolved 2026-07-17 (phase 0). The list was reconciled against the commits and the ticking rule tightened: an item now earns its tick only from a filled playtest checklist, so nobody marks their own homework.

Keystone

The most important task for this target is not on the list at all.

Developer commands are gated on PD_DEV_CMDS, which is set per process, not per account. So a shared server is all or nothing: run it with dev commands and every friend gets self-heal, mob spawning, and instant levels. Run it without and you lose your own tools during the playtest you are hosting. A per-account is_gm flag fixes this, and the column already exists on the accounts table. It is just never read into the world connection. Everything else in this plan waits behind it.

Resolved 2026-07-19 (phase 1 keystone). Dev commands now gate on is_dev || is_gm, with the flag carried in the signed world token, so a hosted server can run with PD_DEV_CMDS off and grant tools to your account alone. Hosting is no longer blocked.

The critical path

Only one chain has to happen in order. Everything else can move.

Per-account is_gm decides whether a shared server can run at all with your own tools intact. Done 2026-07-19.

Hosting could not safely happen until that flag existed, because the alternative was handing every friend the dev commands. The flag is live and the exploit gate closed on 2026-07-31, so this is now the next link.

The first outside session cannot happen until there is something to connect to.

The fix list is largely written by whatever that first session surfaces, so it cannot be fully specified in advance.

Opening to the whole group waits on those fixes.

01

Close the exploit gate

Done Keystone Low risk Jul 20 to Jul 31 · finished on time

The phase that decides whether anyone can be invited. Every item below already had a file and line number named in the July security audit, which is why the risk was low despite the subject matter. All seven gates are built and playtested; each was reviewed adversarially before commit, and two of them were fixed again after playtest caught what review could not.

  • Per-account is_gm. Done (playtested 2026-07-19). Threads the existing accounts column from the signed world token into the connection, and gates dev commands on it instead of the process-wide environment variable. This is what lets you keep your tools on a server your friends are playing on.
  • Respawn dead-check. Done (playtested 2026-07-20). The respawn handler floored health to 25% without checking you actually died, so a living player could top up on demand. Now gated on the awaiting-respawn flag.
  • Attack while seated. Done (playtested 2026-07-20). A swing now stands the attacker, and the seated regen bonus is suppressed in combat. Server + client.
  • Cast class and level gate. Done (playtested 2026-07-22). A cast is refused unless the caster's class is in the spell's list and their level meets its minimum, checked before any mana, cooldown or skill side effect. Every spell in the server table is class and level tagged, locked by a test so an untagged spell cannot silently reject everyone.
  • Attack weapon trust. Done (playtested 2026-07-23). The resolver reads the equipped weapon from the server's own equipment map instead of believing the weapon the client names, so a modified client cannot swing something it has not equipped. An empty hand is an unarmed swing, and an off-hand attack with an empty off-hand is refused outright.
  • Melee swing-rate limit. Done (playtested 2026-07-29). A per-hand minimum interval between swings, derived from the equipped weapon's delay and assuming maximum haste so a hasted player is never throttled. Tracked per hand because dual wield sends two independent streams. Adversarial review caught a second free damage stream here: an off-hand attack with nothing in the off hand.
  • Login rate limiting and auth timing. Done (playtested 2026-07-31). A per-address cap on both login and registration, plus a decoy password check so a missing account takes the same time as a wrong password and cannot be told apart. Playtesting found two faults review had missed: the limit exempted the local machine, which made it both untestable and unprotected there, and the launcher's automatic login after registering reset the shared counter so registration never throttled at all.

Done meansAudit findings 2 through 6 and 9 are closed, the permission flag is live, and the audit's threat list has been re-run against the changed code. All met.

02

Host it, invite one person

Done Highest schedule risk Aug 3 to Aug 7 · finished Aug 11, four days late

The one estimate in this plan that was a guess, because nothing in ten weeks of history had been a deployment. It ran four days over on a one-week phase, which for a guess is a good result. The shape changed twice along the way: the deploy target became a physical server rather than a rented one, and the access model became a private network rather than an open port.

  • Deploy target stood up. Done. A physical Dell PowerEdge R720 rather than a rented server. It arrived unable to boot, so the phase quietly included building the machine from bare metal: two RAID volumes with a hot spare, Ubuntu Server, key-only remote access, a default-deny firewall and automatic security updates.
  • Key handling for a real host. Done. Generated per host, permissions locked down, never committed. The server still refuses to boot without it, which it demonstrated more than once.
  • Production environment. Done, and verified in production. Dev commands are off for everyone, and the operator's tools come solely from the per-account permission flag. Confirmed by watching the server accept a GM-only command while its own boot line reported dev commands disabled.
  • Client build and tester README. Done. The README was rewritten rather than refreshed; it had still claimed the game had no multiplayer.
  • Bug report button. Done. Confirmed working, and its Discord invite replaced, because the old one had expired.
  • One friend, one session. Done 2026-08-11. She registered from her own machine, made a character, killed something, grouped with the operator, and logged out cleanly.
  • Backups, beyond the original scope. Nightly snapshots onto a second physical array, a weekly copy to cloud storage outside the building, and a restore actually tested rather than assumed. Inviting someone onto a server with no backups would have been irresponsible.

Done meansSomebody who is not you, from a machine that is not yours, made an account, made a character, killed something, and logged out cleanly. All met, on her evidence rather than the author's.

What the first session foundTwo things, both now open items. She died, respawned on the spot beside the mobs that had just killed her, and died again twenty seconds later, which is an unwinnable loop for a new player. And the login rate limit, built to stop brute-force attacks, locked her out after five attempts and pushed her into creating a second account rather than waiting a minute. The first real user found both within ten minutes.

03

Stop it eating their things

Aug 10 to Aug 21 In progress

Two categories: bugs that destroy player property, and bugs that only look like they do. The second category costs you testers just as fast as the first.

  • Deposited bank items render as empty slots. Done (playtested 2026-08-17). A deposited item appeared to vanish, and no tester would have believed it was safe. Nothing was ever lost, and it was not the refresh bug everyone assumed: the window repainted correctly every single time and drew nothing, because a vault slot could only draw an icon and a stack count, no item in the game has an icon yet, and the count is hidden for a single item. A blank texture over a blank label looks exactly like an empty slot. It now falls back to the item's name, the way the inventory and bags always have, which is why only the bank ever showed this. The highest perceived-severity bug on the list turned out to be one missing label.
  • An unclean disconnect did not block relogin. The tester killed their client and logged straight back in, which contradicts the design. Re-test first; it may not reproduce.
  • Bank and vendor transfers are not atomic. Two separate writes, so a crash between them dupes or loses. The corpse loot path already solved this and can be copied.
  • Bags open on left-click instead of right-click. Done (playtested 2026-08-18). Not stale pre-grammar bags after all: the click handler opened a bag from the left-click path as well as the right-click one, so both buttons did the same thing and a bag could never be picked up or rearranged at all. Left-click now lifts it, right-click opens it.
  • Inventory desyncs from the server and cannot recover until you relog. Found while playtesting the bag fix, and it belongs in this phase: items appear to stick to the cursor, or to vanish outright. Nothing is actually lost and the server stays correct the whole time, but it reads exactly like the game eating your things. Two separate faults compound, both three months old: when the server refuses a move it tells the client nothing, and the client quietly discards updates it thinks it has no home for. Neither side can correct the other, so it lasts until you relog.
  • Named mobs lost their enrage and guaranteed drops. Both live only on the client with no server side, so every named mob is currently a generic mob wearing a name.
  • Whatever the first friend session surfaces. Leave room here. It will find things.

Done meansNothing loses items, nothing appears to lose items, and a first-time player does not hit an obvious "this is broken" moment in their first hour.

04

An evening's worth of game

Runs parallel Aug 24 to Sep 11

The mechanics are ahead of the content. Four quests and one zone is maybe ninety minutes before a friend runs dry. This is the difference between "I saw your game" and "we played your game on Saturday."

  • Quests and mobs. The quest system is fully server-authoritative now: persistent journals, NPC turn-ins, item rewards, once-per-character dedup. What is missing is authoring capacity, not engineering. The largest and most open-ended item here.
  • Respawn at bind, and a Soul Binder NPC. Done (playtested 2026-08-13). Pulled forward out of this phase because the first outside tester hit an unwinnable death loop: she died, woke beside the mobs that killed her, and died again. Respawn is now decided by the server (your bind point, otherwise the town spawn, never where you fell), Sister Maelis sets the bind, the dead can no longer walk their own corpse around, and enemies break off the moment you die. The cause was not the missing bind point: respawn simply never moved the player at all, and the server is what owns position.
  • Set the corpse decay timer properly. Phase 0 is the emergency raise; this is the considered value.
  • A minimal sound pass. Not yet committed to. See the open question below.

Done meansTwo friends can group up and play three hours without running out of things to do.

One open question

Does the friends build ship silent?

There is currently no audio at all: no combat, no spells, no ambience, no music. To someone who has been building this for months, that is invisible. To a friend logging in for the first time, total silence is one of the loudest things about it.

But the task as written on the to-do list, covering combat, spell, ambient, and music, is a multi-week subsystem rather than a polish pass. The middle path is a minimal version: a swing, a hit, a spell cast, a death, and one ambient loop. Perhaps three days rather than three weeks. That is what Phase 4 assumes. Ship it silent instead and Phase 4 shortens by about half a week, pulling the target date in.

How this gets kept honest

This schedule exists because a to-do list drifted out of sync with reality. It would be a poor showing if the schedule did the same thing, so the rule is one home per fact.

This document tracks phases. The project's to-do list tracks tasks. The bullets under each phase above are the plan for that phase, not a checklist. Their status lives in one place only, so the two can never disagree.

Nothing is ticked until it has been playtested. Not when it compiles, not when the tests pass, not when it is committed. A filled checklist showing it working is the evidence. Until then the task is built, not done.

This document expires. When September 14 arrives, anything unfinished folds back into the to-do list and this gets retired rather than left to rot. That is the failure mode it was written to fix.
