How to read the weeks

Five lanes. Each row is one act that can be checked afterwards: one checklist sitting, one build step, one redeploy, one friend session, one decision. The time column is the user's hours, or Claude's build days, or the date a decision starts to block something. A row with a dashed edge is tentative: it waits on an approval or a decision.

Decide
Who: the user or the planner; each carries the date it starts to block.
Build
Who: Claude, often unattended on days the user is away.
Operate
Who: the user at a desk: redeploy, export, zip, send.
Verify
Who: the user running a checklist, sometimes with a second seat.
People
Who: friends: onboarding, the rehearsal, the evening itself.

Assumptions

  • A checklist row takes about six minutes to run, so a sitting of 15 to 20 rows is one and a half to two hours. Source: This project's own sittings (handoff note, 2026-10-05); phase 4's 28 rows ran across five sittings.
  • A redeploy costs the user about fifteen minutes and takes the world down for about two minutes. Everyone online loses up to a minute of progress, so people log out first. Source: docs/deployment/server_operations.md; the 2026-10-05 redeploy was down about two minutes.
  • An export plus zipping and sending it costs about an hour of the user's time. No export has been timed; this is a guess. Source: Assumption.
  • Build steps are laid out at roughly half the pace the plan file estimates, with a review pass folded into each. That is the schedule's own rule (two-week windows for work measured at three days), because the history holds real gaps of three and ten days. Source: docs/schedule.md section 1; docs/design/spell_batch_plan_2026_10_05.md step estimates.
  • Onboarding one friend costs the user about thirty minutes (share link, zip, README, check the account list), plus the friend's own install time. Source: docs/deployment/inviting_a_player.md, steps 2 to 5.
  • The user has about thirty hours a week. Weeks here never schedule more than half of it, because the pile of unverified work has been the recurring risk, not a shortage of plans. Source: docs/schedule.md header.
  • Every date here except November 8 is a proposal. The milestones were placed by working back from November 8 at the measured pace with the fifth week left as slack. Source: The handoff's instruction; docs/schedule.md section 1.

Words used here

The R720. The physical server in the basement that runs the game for everyone. Reachable only over Tailscale, a private network each tester joins once.
Redeploy. Putting a new server build on the R720. The user's job, about fifteen minutes; the world is down about two minutes. A server change reaches players only this way.
Export. Building a new game client (the program testers run) from the Godot editor, then zipping it and sending it. A client change reaches players only this way; the server needs nothing.
Protocol bump. A change to the language the client and server speak. Afterwards an old client cannot connect at all, so the server and the new client must change on the same evening and every tester needs the new zip.
Second seat (two-boxing). A row that needs two players in the world at once. The user can run two accounts on one machine, so no friend is required for these.
Checklist. A file in docs/playtest_notes/ with one row per thing to try in the game. Filling it is how built work becomes done. The counts on this page are rows still to run; the verdicts live in the file.
The To-Do. The list in CLAUDE.md. The only place an item's status lives. Nothing on this page says whether something passed.
GM. The one account with developer tools (spawn a creature, grant a level, give an item). Only the user's account has it; friends never do.
Tentative. Work that waits on an approval or a decision. Shown so the whole picture is visible, styled differently so it is never mistaken for a commitment.

How this stays current

One home per fact. This page carries dates, sequence, owner and dependencies. The To-Do carries status. The checklists carry verdicts. The schedule carries the phases. The plan file docs/schedule_detail.toml is the only thing a person edits here; both this page and its markdown twin are generated from it.

Claude regenerates this page in every session that changes a To-Do status or a checklist, as part of the session workflow. The procedure:

  1. Run python tools/schedule_detail.py from the repo root. It stops with an error if any row names a checklist or To-Do entry that no longer exists.
  2. Read its report. An unscheduled checklist with open rows, or a scheduled checklist with none left, means the plan file needs a row added, moved or removed. Edit it and rerun.
  3. Commit the plan file with both generated files, and republish this page at its link.
